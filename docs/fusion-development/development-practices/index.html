开发实践

融合开发中的问题往往出现在资源从源码进入运行环境的过程中：文件存在，可能没有打进 JAR；JAR 构建完成，实例可能仍加载旧版本；页面可以访问，后台调用却缺少相同的身份和事务。本页按这些具体环节介绍检查和处理方法。

新功能先贯通一个业务入口​

新增一个页面时，先把页面、路由、菜单、权限和实际接口连起来，再扩展交互。这样可以尽早发现资源标识不一致或注册位置错误。

资源需要核对的关系
模块定义功能归属和模块层级正确
菜单指向实际存在的页面路由
权限菜单、UI 视图和接口的访问范围一致
UI 模型路由对应正确的渲染类型、Schema 或微前端
UI Schema / 微前端请求正确接口，加载与错误状态可辨认
后端实现正常、无权限和无效输入都有可核对的结果

可以使用 tidestack-business-entry-definition 辅助联动维护这组资源。验收时用目标业务账号从菜单进入，再直接调用接口，分别验证页面与服务端权限。

模型资源未生效，沿加载链路检查​

依次核对 源码 → 构建输出 → JAR → 实例 → 资源发现 → 业务使用。在哪一环第一次缺失，就回到该环修复。

对独立 Maven 模块，可以先执行资源处理：

mvn process-resources

检查 target/classes/META-INF/ouroboros/metadata/。完整打包后，再检查实际准备部署的 JAR：

jar tf target/myapp-orders-1.0.0-SNAPSHOT.jar

如果只有 src/main/metadata 中存在文件，补齐资源复制配置；如果 JAR 中有、实例中没有，核对上传位置和当前产物版本。若资源已经被发现，再检查唯一名、跨资源引用和合并结果。

修改生成目录里的文件只能影响本次输出。应回到源码修复，再重新构建。文件后缀、固定集合文件和 JAR 内路径见 模型资源与打包。

自动配置、SPI 与组件扫描分别处理​

三种机制承担不同职责：

  • 自动配置 把模块接入应用，按模块约定登记 AutoConfiguration.imports 与 spring.factories。
  • 组件扫描 在已经装配的模块中发现 Service、Controller 等 Bean。
  • SPI 在 META-INF/services/<接口全限定名> 中登记实现，交给对应注册与发现机制消费。

普通业务模块扫描自己的包。某个基座能力没有装配时，先检查依赖和注册；扩大启动类的扫描范围，会把更多内部组件带入当前应用，增加重复 Bean 或错误装配的可能。

如果实现需要 Spring Bean，按该扩展点既有的 Spring/SPI 桥接方式接入。具体示例见 后端扩展包 和 平台扩展点。

依赖冲突先看树和基座清单​

出现 NoSuchMethodError、类找不到或同名 Bean 时，先核对实际加载版本，再修改依赖：

mvn dependency:tree -Dincludes=com.ouroboros
mvn dependency:tree

标准基座扩展模式还应对照 runtime manifest 和依赖过滤报告，确认扩展是否重复携带基座库、是否保留了异版本依赖，以及新引入的库是否真的进入交付目录。过滤规则见 Maven 构建与依赖过滤。

内嵌基座模式则检查启动模块的完整运行依赖。BOM、Spring Boot 与基础库版本应统一管理，不能用扩展包的 provided 规则把启动程序本身需要的运行库排除掉。

让开发配置与运行配置各有归属​

数据库、端口、文件目录和基础设施连接由 Spring 配置及部署环境提供。运行期需要管理的业务参数，通过平台配置项声明，再由业务代码读取统一配置能力。

情况建议位置
本机数据库、后端端口、调试连接私有 application-local.yml 等本地文件
随业务模块交付的配置项与分组定义configurations.json、configuration-groups.json
平台编辑的单个配置定义应用目录中对应的配置文件
现场凭据和实例差异部署环境配置来源

JAR 中的集合定义与应用目录的单项文件采用不同形态。IDE 能创建某个文件，仍要确认该位置的 Provider 会读取它。配置值也要在实际运行实例中检查，本地 YAML 中存在某个 key 不能说明业务代码已经使用它。

复用统一缓存与自适应分布式锁​

缓存空间按业务命名，key 中包含必要的租户或业务标识，过期时间按数据可接受的陈旧程度设置。使用 CacheManager.getOrPut 时，优先选带 Class<T> 的类型安全重载，避免不同调用把同一个 key 读成不同类型。

DistributedLockManager.getLockManager() 通过 SPI 选择锁实现；没有对应实现时会回退到本地锁。本地锁只能协调同一进程，部署多个副本前，应确认实际装配了跨进程实现。

锁 key 应标识需要互斥的业务资源。成功取得锁后，在 finally 中释放；同时确认等待和持有时间适合任务长度。锁不能替代数据库事务或消息幂等检查。

参数绑定异常时检查编译参数​

模型动作、表达式或框架反射需要识别 Java 参数名时，编译器应保留参数名。Maven 编译配置使用：

<parameters>true</parameters>

平台后端模板已经包含这项配置。接入已有工程时，检查实际生效的 compiler 配置；改完后重新编译，旧 class 文件不会因为修改 POM 自动获得参数名。

后台调用显式安排身份与事务​

Controller 请求、消息消费、计划任务和异步逻辑流不处于相同执行环境。把一段浏览器请求中的业务代码移到后台后，不能继续假定存在当前用户、租户或原请求事务。

按调用方约定显式提供执行身份和所需上下文，并围绕一次完整业务操作安排事务，代码示例见 事务、异常与后台身份。数据读写继续走数据模型 API；无权限、重试和重复消息等场景在相应入口验证。入口接入方式见 消息队列、计划任务 和 业务模型。

前端联调保持宿主入口​

调试业务微前端时，先确认前端基座、后端和微前端开发服务器三个地址，再检查宿主访问路径如何代理到目标服务。直接打开微前端开发服务器，可能缺少宿主提供的登录、路由和上下文。

静态资源 404 时检查入口、publicPath 和资源请求路径；API 失败时检查代理目标、请求凭据和登录跳转；页面空白时，同时看地址、网络响应与渲染错误。代理参数见 前端联调工具。

区分源码更新、模型刷新与 JVM 重启​

修改 Java、自动配置、SPI 或 JAR 内资源后，重新构建并让目标实例加载新产物；需要更换 JVM classpath 时重启实例。应用目录中模型文件的刷新，则按对应模块的加载与刷新机制操作。

联调记录中保留实例、源码提交、JAR 和业务请求。断点不命中时，先确认它们对应同一次变更。不要通过复制同名基座类、关闭初始化监听器或放开全部权限，让本地结果暂时通过；应修正注册、版本、配置或刷新环节。

提高构建速度时保留验证边界​

多模块工程可用 mvn -pl <模块> -am test 构建目标及其上游。只验证一个测试类时，给上游没有匹配测试的模块配置 -Dsurefire.failIfNoSpecifiedTests=false，避免测试选择规则阻断 reactor。

平台源码仓库另提供 scripts/agent-feedback/verify-fast.sh，用于定向反馈。它默认离线执行并跳过多项质量门禁，需要已经具备依赖缓存；最终仍应完成所需门禁和集成验证。普通应用工程优先使用自己的测试入口。

代码测试通过后，再用实际交付包检查启动、资源发现和关键业务。打包成功、Schema 校验通过以及真实业务可用，分别提供不同范围的证据。
