# 模型变更与应用升级

已经有数据的应用，升级时需要同时处理模型定义、物理结构和已有记录。修改模型并构建成功，只能说明新定义已产出；还要确认旧记录能被读取、新规则可以满足，上一版程序在必要时仍有恢复路径。

本页以 [物料登记示例](./first-feature)新增分类字段为例，说明怎样在保留旧数据的前提下推进变更。应用版本、镜像和备份的运维操作见 [业务应用发布与回退](../operations/application-release-and-rollback)。

## 先分清四类变更

| 变更 | 例子 | 需要处理的对象 |
| --- | --- | --- |
| 展示或逻辑调整 | 改标题、页面排列、规则 | 元数据、代码及其引用 |
| 结构变更 | 新增字段、调整容量、索引和约束 | 模型与目标数据库结构 |
| 数据变更 | 为旧物料补分类、转换旧状态值 | 已有记录及变换规则 |
| 身份变更 | 改模型全名、表名、字段存储名 | 所有引用、旧结构、数据映射和兼容期 |

同一次需求可能包含多类。例如把一个可选字段改为必填，既要改变模型规则，也要先处理旧记录中的空值。给字段增加默认值，不能据此判断历史记录已经回填。

## 确认结构由谁迁移

注解模型通过 `@Model.migrationStrategy` 声明迁移策略；默认是 `MigrationStrategy.AUTO`。SQL 数据站自身也有策略，数据站关闭自动迁移时，不会因为模型设为 `AUTO` 就自动执行。

- 使用自动迁移时，在预演环境核对实际生成的 SQL、执行结果和启动日志。
- 由团队数据库变更流程管理时，把对应模型设为 `DISABLED`，先准备匹配结构，再部署应用。已有工程的正式机制优先沿用。

当前 SQL 迁移会将模型目标结构与已有数据库快照合并，保留已有表列，并对类型变化作兼容性判断。兼容扩容可以进入迁移；缩短容量或不兼容类型变化不会按模型文字直接强制转换。模型删除字段，也不代表物理列及其数据会随之删除。

因此，自动迁移适合经过验证的结构演进，不提供任意改名、清洗数据或恢复旧结构的保证。部署日志中出现“类型不兼容，将不会自动修改”时，要处理真实结构差异，不能只因为应用继续启动就认定升级完成。

## 新增分类字段，先允许旧记录为空

在 `Material` 中增加可选字段和访问器：

```java
@Field(label = "分类", size = 64, nullable = true)
private String category;

public String getCategory() { return category; }
public void setCategory(String category) { this.category = category; }
```

第一版先允许为空，保留 `sample.Material`、`sample_material` 和现有字段存储名。更新 DTO、Service 和页面时，也要允许尚未补分类的旧记录正常读取。

在旧版本数据副本中启动这一版，检查：

1. 原有物料数量、ID、编码和名称保持一致。
2. 新分类字段可以读取，旧记录通常为 `null`，不会凭空获得某个分类。
3. 新登记的物料按当前接口约定保存分类。
4. 旧版页面、接口调用方和后台任务仍可使用兼容输入。

下载工程中的 `MaterialMigrationTest` 先建立旧模型并写入一条物料，再用包含可选分类的元数据迁移，最后验证旧名称、空分类和分类更新结果：

```bash
mvn test -Dtest=MaterialMigrationTest
```

该测试使用 H2 验证基础行为。发布前仍需用生产同类数据库和有代表性的旧数据预演，尤其是大表、索引、字段类型和非空约束。

## 查看迁移计划后再执行

已有 `SqlDataStation` 对象时，可以生成迁移 SQL：

```java
var sql = station.generateMigrationSql(station.getDataModelList());
if (sql.isLeft()) {
  throw new IllegalStateException("生成迁移 SQL 失败", sql.getLeft());
}
sql.get().forEach(System.out::println);
```

`station` 使用目标环境的数据源、方言和本次模型集合。生成过程读取真实结构快照，不等于执行迁移；示例中的 `migrate()` 才会执行。诊断和预演应从受控工具或测试运行，不要为此增加公开的管理接口。

审核时特别确认表名、列名、容量、约束以及可能持锁的操作。空白数据库上的建表计划不能代替已有数据的升级计划。执行后再次核对实际结构，DDL 的事务与隐式提交行为以目标数据库为准。

## 单独回填已有数据

先确定旧物料的分类如何得出。可以可靠归为 `GENERAL` 的记录，才使用这个默认分类；无法判断的记录保留待处理状态或交给业务人员确认，不应为满足非空约束随意填值。

回填通过正式数据模型 API 或现有迁移作业执行。例如，下面的处理只修改确实尚未分类的指定记录：

```java
var model = DataModelCenter.getDataModel("sample.Material")
    .orElseThrow(() -> new BusinessException("物料模型尚未加载"));
var where = new java.util.HashMap<String, Object>();
where.put("id", materialId);
where.put("category", null);
long updated = model.update(where, Map.of("category", "GENERAL")).get();
```

`materialId` 来自当前批次的旧记录。更新条件限制分类为空，避免覆盖其他人已经设置的分类。Java 的 `Map.of` 不接受 `null`，因此空值条件使用普通 Map。`updated` 为零时，重新核对该记录是否已处理或已被其他操作修改。

大批量处理按稳定主键分批，记录批次进度、成功数和失败项，并验证实际更新行数。

回填规则应能安全重跑：已完成记录不重复覆盖，失败批次可以继续。对会改变原值的转换，保存原值或变换前快照，才能为恢复提供依据。`.data-init.json` 只补缺失记录，不用于这类回填。

## 等数据满足规则后再收紧约束

确认所有旧数据已处理、新入口都能提交分类后，再将业务规则改为必填。模型校验和数据库非空约束需要分别核对，二者不能只改一处就假定同步完成。

当前 SQL 迁移对普通的“可空改非空”有保护行为，不会默认强制收紧。需要按“先补齐、再收紧”流程管理物理非空约束时，字段支持 `requireAfterBackfill` 选项：

```java
@Field(label = "分类", size = 64, nullable = false,
    extraProps = {"requireAfterBackfill", "true"})
private String category;
```

该选项会在已有表中检查空值：新列尚未建立，或旧列仍有空值时，先保留物理可空；数据补齐后再次迁移，才进入非空约束变更。它不负责回填，也不能让旧版本客户端自动提供分类。

启用前确认目标基座版本支持该选项，预演两次迁移并检查实际约束。由数据库变更流程管理结构时，沿用同样的先后顺序，通过正式变更收紧约束。

## 改名、转换类型与删除字段

### 只改展示名称

改 `label`、页面标题或说明文字，保留稳定标识与存储名。检查页面、导出与错误提示是否一致，一般不需要搬迁业务数据。

### 改模型全名或存储名

模型全名是引用标识，`rawName` 是物理存储名。直接修改可能被视为另一个模型、表或列，运行时不会据此理解“将旧数据重命名后搬过去”。先列出引用、映射、兼容入口和迁移步骤，再安排切换。

### 转换字段类型

先在数据副本中检查无法转换的旧值、精度损失、容量和索引影响。通常先增加新字段，按明确规则转换并核对结果，再切换读写；旧字段保留一个兼容期，最后单独安排清理。不要把自动迁移的兼容性保护当作已经完成业务转换。

### 停用旧字段

先停止新代码写入，排查页面、流程、接口、报表和外部消费者的引用，再逐步停止读取。当前自动迁移保留旧列，清理物理数据需要另行审核，不能通过删掉模型字段来验证数据已清理。

## 演练升级与回退

准备上一版应用资产、配套基座镜像和脱敏数据库副本，按正式顺序部署新资产、执行结构变更、回填、验证业务，再尝试恢复上一版程序。

至少核对以下结果：

- 旧记录数量、主键、关联和代表性字段未被意外改变。
- 新旧数据都能查询，登记、修改、业务动作与权限符合新规则。
- 升级过程重复执行不会重复造数或覆盖已处理数据。
- 上一版程序是否兼容升级后的结构，以及是否仍能读取新写入的数据。

只增加可选字段通常更容易保留程序回退空间，但仍需验证旧程序对额外字段的处理。类型转换、强制非空和数据覆盖可能使旧程序无法工作；恢复旧 JAR 不会撤销这些变化。

发布时记录应用元数据提交、扩展版本、基座 digest、结构计划、回填批次和备份位置。出现不兼容故障时先停止新写入，保存现场，再按事先演练的方案恢复程序或数据库。数据库恢复会影响备份之后的写入，需要在发布方案中明确允许的数据窗口。
