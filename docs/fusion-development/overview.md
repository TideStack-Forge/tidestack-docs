# 融合开发总览

融合开发围绕同一份业务定义组织配置、生成、实现和验证。开发者明确要实现的行为，平台模型保存业务语义，AI 据此读取已有资产、提出改动并完成实现，结果再进入平台现有的加载和运行链路。

## 共同的开发依据

业务对象、字段、关系、动作、事件与权限决定应用要做什么。可视化编辑器中的修改和 AI 生成的元数据都需要遵守这些定义。需要组件、服务或适配器时，其输入输出也要与模型保持一致。

[建模体系](../concepts/modeling/)说明各类模型的职责；[模型资源与打包](../guide/advance/authoring-metadata-conventions/)说明模块资源的源码与打包位置。AI 读取这些定义后，才能确定要改哪些文件、复用哪些能力，以及如何检查结果。

## 一次功能开发如何推进

| 阶段 | 开发者与 AI 要完成的工作 | 检查结果 |
| --- | --- | --- |
| 描述需求 | 明确使用者、业务动作、规则、异常和访问范围 | 有具体输入及预期结果 |
| 理解现状 | 读取目标版本、已有模型、页面、流程、接口和测试 | 找到现有入口与可复用能力 |
| 拆解改动 | 确定模型、配置、页面及实现各自需要的变化 | 变更清单与业务目标对应 |
| 完成实现 | 在编辑器中配置，或由 AI 修改元数据和代码 | 资源、引用、注册和行为测试齐全 |
| 联调验证 | 在测试应用触发真实业务，核对页面、接口和数据 | 正常、失败、无权限场景有实际结果 |
| 评审交付 | 评审变更与证据，记录配套版本及恢复步骤 | 交付物可维护、可追溯、可回退 |

这些步骤可以在同一次任务中反复执行。运行结果不符合预期时，将复现条件和日志带回实现环节，修正最先出错的位置。

## 模型与实现如何配合

标准对象、页面、权限和流程使用平台已有的模型与配置。AI 可以根据现有样例生成或调整这些定义，再由开发者在平台中检查投影、页面和运行结果。

当需求需要新的交互或程序能力时，使用平台正式扩展点承载。前端实现以微前端、布局或组件形式被引用；后端实现通过 JAR 中的 SPI、自动配置和元数据被发现。业务定义继续引用这些能力，保持一致的权限与生命周期。

实现位置由需求和平台契约决定。AI 可以参与整个过程，具体技术方式见 [平台扩展点总表](./extension-points)。

## 提供上下文，取得运行证据

给 AI 的上下文至少包含目标版本、工作位置、相关业务定义和验收数据。具体示例见 [用 AI 完成功能开发](./ai-assisted-development)。文档检索提供公开约定，当前项目文件提供实现依据，实例状态和业务请求提供运行证据。

可使用当前环境已有的 IDE、项目脚本或 MCP 工具读取、修改和校验。工具是否可用及其执行范围以实际接入为准，不能把生成方案当作已经执行的结果。

## 完成标准

- 需求中约定的业务行为已经实现，模型与实际调用一致。
- 元数据引用、代码注册、依赖和资源路径符合目标版本契约。
- 页面和直接 API 调用均遵守权限，异常结果可以定位。
- 测试、构建、加载与业务验证分别说明结果和未覆盖项。
- 配套模型、前后端产物、配置与平台版本可追溯，恢复方式明确。

团队如何评审和接收成果，见 [任务协作与交付验收](./high-low-code-collaboration)。
