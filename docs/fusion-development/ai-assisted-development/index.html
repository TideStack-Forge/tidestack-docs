用 AI 完成功能开发

把一个功能交给 AI 时，需要同时提供业务目标、当前应用的依据和验收方式。AI 可以协助修改模型、页面、流程和扩展实现；交付结果应进入项目已有资产，并能在目标应用中验证。

本页以“为已有采购订单增加风险检查”为示例组织任务。示例描述开发过程，具体模型名、状态、接口及规则以目标项目为准。

1. 提供任务上下文​

先按 AI 入口让助手能够读取手册，再提供目标版本、工作位置和相关业务定义。手册说明平台用法，项目文件说明当前实现，运行实例提供实际状态。

示例任务可以这样描述：

目标：为已有采购订单增加风险检查。
位置：<工作区、应用或模块>；平台版本：<目标版本>。
已有资产：<采购订单模型、页面、动作、外部检查接口和相关测试>。
业务规则：<允许检查的状态、调用条件、结果与超时处理>。
权限：<谁可发起、谁可查看；无权限时的预期行为>。
验收数据：<通过、未通过、超时和无权限的测试场景>。

先读取项目约定、已有模型与实现，说明可以复用的能力和需要修改的位置。
业务规则缺失时列出待确认项。沿用平台模型、加载、权限和发布机制。
完成后报告实际改动、执行的检查和仍未验证的场景。

外部接口提供参数、响应、错误和测试样例即可；凭据通过环境既有配置传入。上下文与工具的选择见 知识来源与工具边界。

2. 先确定变更，再生成实现​

让 AI 将需求对应到现有资产：订单动作是否存在、检查结果保存在哪里、页面从哪里读取状态、接口如何授权。可先完成一个最小路径，再增加异常与边界场景。

例如，现有外部接口已经支持检查时，可以复用接口与逻辑流实现动作；需要专用 SDK 时，将适配放到正式后端扩展中，再由同一业务动作引用。页面继续读取模型和接口的真实结果。

确定改动范围的方法见 从需求确定实现范围，实现位置见 平台扩展点总表。

3. 在已有资产中完成修改​

任务结果AI 需要参考什么修改后核对什么
模型与元数据同类定义、资源打包约定、目标类型和 Schema文件后缀、业务语义、引用与投影
页面与交互UI 模型、Schema、接口及 SDK 契约数据域、状态更新、错误与权限
规则与流程动作契约、现有节点与脚本上下文输入输出、执行顺序、失败及重复操作
程序能力扩展接口、现有实现、依赖和注册文件行为测试、构建、SPI、装配与消费入口

修改应保留当前项目的架构与开发约定。生成的文件需要纳入同一版本管理流程，后续按所属模型既有的保存、导出和构建方式继续维护。

4. 分层验证​

  1. 结构与引用。 检查 JSON、Schema、字段、资源名称及跨模型引用。Schema 未描述的语义还需核对目标类型和项目定义。
  2. 构建与行为。 对涉及的模块执行构建与相关测试，验证输入、结果及失败分支。仅调整配置时使用已有配置校验和回归入口。
  3. 加载与装配。 在目标实例确认元数据、组件、SPI 和自动配置实际生效。
  4. 业务与权限。 用示例任务中的测试数据完成检查，核对订单状态、页面提示、直接 API 调用和权限。

让 AI 使用环境已有的工具或项目脚本执行这些检查。没有测试实例或执行能力时，保留待执行项和复现步骤，不把推断写成验证结果。

5. 根据反馈修正​

检查未通过时，提供复现步骤、输入、实际响应、日志和当前产物版本。先判断偏差发生在定义、打包、加载还是调用阶段，再修正对应位置并重跑受影响的检查。

例如，页面没有展示风险结果时，先核对请求与数据域；节点未被发现时，核对注册和装配；实例运行的 JAR 与源码不一致时，重新构建上传并联调。后端断点调试见 本地 IDE 与线上平台联调。

6. 评审和交付​

最终评审需求对应的变更与实际证据，记录模型、配置、前后端产物及平台版本。操作过程中的任务描述用于解释意图，交付后以项目文件、测试与版本记录保存可维护的结果。

团队分工、交接与验收见 任务协作与交付验收，环境和版本准备见 开发平台辅助能力。
