# 何时用低代码，何时写代码

按最终交付物判断，而不是按实现难度判断。

## 判断表

| 判断问题 | 使用低代码 | 编写扩展代码 |
| --- | --- | --- |
| 交付物是什么 | 一个业务对象、页面或流程 | 一种新的可复用程序能力 |
| 现有模型和组件能否表达 | 能 | 不能 |
| 谁长期维护 | 业务开发人员 | 专业开发人员 |
| 是否需要独立单元测试和发布周期 | 通常不需要 | 需要 |
| 是否接入外部 SDK 或专用协议 | 否 | 是 |

## 直接使用低代码

- 定义字段、关系、列表、表单和详情。
- 配置角色、数据范围、通知和运行参数。
- 使用现有表达式、脚本对象和逻辑流节点。
- 编排标准审批流程。

## 直接进入扩展开发

- 需要新增字段类型、表达式函数、脚本上下文或逻辑流节点。
- 需要独立前端应用、专用交互或大型第三方组件。
- 需要接入企业 SDK、定制认证协议或消息协议。
- 同一能力需要被多个应用安装和版本化。

## 不确定时的验证方法

1. 写出阻塞需求的最小示例。
2. 在 [平台能力地图](../reference/platform-capability-map) 和 [扩展点总表](./extension-points) 中查询。
3. 能由现有能力组合完成时留在低代码；必须新增平台能力时编写扩展。

不要先制作一个低代码版本再整体重写。边界确定后，只把无法表达的部分交给扩展点。
