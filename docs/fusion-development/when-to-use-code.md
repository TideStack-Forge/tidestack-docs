# 从需求确定实现范围

开始开发前，先把业务目标落到已有模型与运行入口，再确定需要改变什么。可视化配置和 AI 实现可以在同一任务中配合使用，最终都要得到符合业务规则的应用行为。

## 把需求写成可验证的行为

例如，“增加采购订单风险检查”还不足以开始实现，需要继续明确：

- 谁能发起检查，哪些状态的订单允许检查。
- 检查使用哪些订单信息，依据什么规则或外部结果。
- 通过、未通过、超时分别如何影响订单状态和页面提示。
- 谁能查看检查结果，结果是否需要记录和追溯。

这些是示例任务需要确认的规则，不代表平台已经内建采购风险功能。真实任务应使用自己的业务定义和验收数据。

## 先找到已有资产

让 AI 或开发者读取目标应用的业务模型、动作、页面、逻辑流、外部接口和权限定义，列出可以复用的部分。在 [平台能力地图](../reference/platform-capability-map) 中定位内建能力，再核对目标版本和项目实现。

如果现有业务动作已经表达同一行为，应调整或扩展该动作；如果标准页面已经由模型生成，应先检查模型定义及投影，避免再维护一份重复页面或接口。

## 按变化对象拆解

| 需要改变什么 | 首选落点 | 需要检查的关系 |
| --- | --- | --- |
| 对象、字段、关系、业务动作 | 业务模型及已有处理入口 | 标识、输入输出、状态与权限 |
| 标准表单、列表、详情 | 模型视图或 UI Schema | 模型投影、数据域与接口 |
| 规则与自动处理 | 表达式、脚本或逻辑流 | 上下文、执行顺序与失败分支 |
| 外部系统交互 | 外部接口、消息及已有适配 | 认证、映射、超时与重复处理 |
| 特殊交互或可复用控件 | 页面、组件或微前端 | 宿主契约、生命周期与资源引用 |
| 平台未提供的程序能力 | 正式后端扩展点 | SPI、自动配置、元数据与消费入口 |

可以让 AI 生成或修改表中的模型、配置和实现。采用哪一种技术落点，取决于业务行为和已有机制；操作方式不改变它应遵守的契约。

## 形成一次可执行任务

任务说明需要列出：目标版本与工作区、相关资产、允许修改的范围、必要的新增能力，以及验收场景。对尚未确定的规则，先列为待确认项，不让 AI 自行补成业务事实。

采购风险检查的第一步可以只是“读取当前订单模型与已有检查接口，列出动作和页面需要的改动”。规则明确后，再实现调用、状态更新与失败处理，最后验证页面和直接接口请求。

具体如何组织 AI 执行，见 [用 AI 完成功能开发](./ai-assisted-development)；需要新增能力时，查 [平台扩展点总表](./extension-points)。
