# 选择工程模式

潮汐栈既可以作为依赖装配进自己的应用，也可以提供标准运行基座，由它加载应用的模型、前端和后端扩展。两种方式都使用同一套模型、自动配置和插件机制，差别在于谁负责组装与交付运行程序。

## 两种模式

| 对比项 | [内嵌基座模式](./embedded-runtime) | [标准基座扩展模式](./standard-runtime) |
| --- | --- | --- |
| 启动入口 | 应用自己的 Spring Boot 启动类 | 标准统一运行时基座的启动类 |
| 基座能力 | 作为 Maven 依赖进入应用工程 | 由基座镜像或运行包提供 |
| 业务实现 | 普通业务模块，与基座共同装配 | 普通扩展 JAR，由基座加载 |
| 模型资源 | 主要随业务模块 JAR 交付，也可使用应用元数据目录 | 应用元数据目录与扩展 JAR 共同提供 |
| 交付物 | 应用自己的启动程序、依赖和镜像 | 固定版本的基座，加上模型、扩展包和前端包 |
| 团队负责 | 应用装配、运行依赖、启动配置和镜像维护 | 应用资产、扩展依赖和与基座的版本配套 |
| 适合项目 | 以代码工程为主体，需要自主裁剪和集成运行能力 | 以平台应用为主体，希望复用标准运行环境 |
| 典型结构 | 领域模块、业务模块和 Web 启动模块 | 元数据、业务扩展、前端及部署工程 |

扩展 JAR 通常与基座代码运行在同一个 JVM 中。设备网关、外部服务等独立进程，仍通过接口或消息与应用集成。

## 怎样选择

已经有成熟的 Spring Boot 工程，需要保留自己的启动入口、依赖治理和部署体系时，选择内嵌基座模式。把需要的模型、权限、逻辑流等能力接进现有工程，业务模块继续按原有边界组织。

从开发平台创建应用，主要通过业务模型、页面和流程开发，再补充 Java 能力时，选择标准基座扩展模式。标准基座负责启动和加载，团队维护业务资产及其配套版本。

选择内嵌模式后，仍可以使用 IDE 元数据编辑器、微前端和平台插件；选择标准基座后，也可以编写完整的业务 Service 和 Controller。实现复杂度本身不决定工程模式。

## 仓库怎么组织

单仓多模块和多仓聚合都能承载上述两种模式。

- **单仓多模块**：后端模块、前端和构建脚本统一评审，适合共同演进的产品。
- **多仓聚合**：元数据、业务服务、前端、网关和部署各有版本，通过聚合仓库固定组合。可以使用 Git submodule 记录这些工程的具体提交。

多仓聚合时，一次交付应能还原整组提交，而不只记录某个服务版本。单仓项目也需要记录基座依赖或镜像的实际版本，不能仅依赖会变化的 SNAPSHOT 标签。

## 开始搭建

先按所选模式建立启动与构建链路，再接入业务模型和页面：

- [标准基座扩展模式](./standard-runtime)：组织应用元数据、扩展包与前端，固定基座版本。
- [内嵌基座模式](./embedded-runtime)：建立启动模块，装配业务模块和基座能力。

工程准备中的 IDE、模板、Schema、Maven 插件和联调脚本见 [开发工具](../development-tools)。资源未生效、依赖冲突及联调定位见 [开发实践](../development-practices)。

使用 AI 初始化工程时，可调用 `tidestack-project-initialization`，提供目标目录、Maven 坐标、平台版本和所选模式。它沿用官方模板与 archetype，并分别安排启动装配、类型化模型编译和扩展依赖过滤。
