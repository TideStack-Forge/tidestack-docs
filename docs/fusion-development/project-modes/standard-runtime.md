# 标准基座扩展模式

标准基座扩展模式使用潮汐栈提供的统一运行时基座。团队维护应用元数据、普通后端扩展 JAR 和前端包，由基座负责启动、发现并运行这些资产。增加业务功能时，通常更新应用资产即可；升级基座时，再单独核对基座版本与兼容性。

## 组织应用工程

元数据、业务服务、前端和部署工程可以放在同一仓库，也可以分成多个 Git submodule，由聚合仓库记录它们的版本组合：

```text
myapp/
├── metadata/                      # 应用模型与运行定义
├── service/                       # Java 扩展工程，产出普通 JAR
├── web/
│   ├── micro-app-business/         # 业务微前端
│   ├── component-library/          # 组件库
│   └── custom-login/               # 自定义登录页
├── gateway/                       # 按需部署的独立网关服务
├── deploy/                        # 基座版本、环境配置和部署编排
└── script/                        # 构建、装配与检查入口
```

聚合仓库里的 `service` 是业务扩展工程，它在正式运行时由标准基座加载。网关等独立服务有自己的进程与部署边界，通过接口或消息接入。

使用 submodule 时，按聚合仓库记录的提交初始化工程：

```bash
git clone --recurse-submodules <聚合仓库地址>
git submodule update --init --recursive
git submodule status --recursive
```

需要升级某个子工程时，先验证该工程，再把新的子模块提交指针记录到聚合仓库。按远端最新分支自动更新所有子模块，会改变原来固定的交付组合，不适合作为复现旧版本的步骤。

## 划分资源归属

同一份资源应有明确的维护位置。随代码复用的定义可以进入 JAR，应用及现场定制可以放在应用元数据目录。

| 资产 | 维护位置 | 构建或运行落点 |
| --- | --- | --- |
| 应用业务模型、逻辑流、页面等 | `metadata/` 中对应类型的目录 | 应用元数据目录，由文件系统 Provider 加载 |
| 扩展自带的菜单、权限、模型等 | `service/src/main/metadata/` | 扩展 JAR 的 `META-INF/ouroboros/metadata/` |
| 自动配置与 SPI | `service/src/main/resources/META-INF/` | 扩展 JAR 中相同注册路径 |
| 后端业务实现 | `service/src/main/java/` | 扩展 JAR 及需要补充的运行依赖 |
| 前端实现 | `web/` 下各工程 | 微前端 ZIP 与其注册定义 |
| 环境连接、密钥和实例设置 | 部署环境的配置来源 | 实例实际读取的配置文件或环境变量 |

应用元数据目录沿用平台各开发模块的文件布局，例如 `business-model/`、`logic-flow/`、`ui-model/` 和 `ui-schema/`。JAR 内则使用按业务组织的 `metadata` 与类型后缀，二者的目录布局不能直接互换。后缀与打包约定见 [模型资源与打包](../../guide/advance/authoring-metadata-conventions/)。

需要覆盖随包定义时，先确认目标类型的标识、来源优先级和合并规则。不要在 JAR 和应用目录中各放一份长期独立维护的同名定义。

## 开发后端扩展

从 [后端扩展包](../backend-extension-packages) 的模板起步，使用与目标基座一致的 BOM，并按自动配置、SPI 和资源约定注册实现。

正式交付的扩展是普通库 JAR。基座提供的 API 通常以 `provided` 引用；扩展额外需要的第三方依赖，经过依赖过滤和兼容性核对后随包交付。不要把扩展重新打包为包含另一套 Spring Boot 运行环境的可执行 JAR。

Java `@Model` 类需要生成类型化查询字段时，启用模板中的 `typed-data-model` profile。类型化编译和扩展依赖过滤可以同时使用：前者负责生成 `*Meta`，后者在交付时剔除基座已有依赖，见 [开发工具](../development-tools)。

扩展可以使用本地测试启动类进行调试。在 `src/test/java` 中创建 `TestApplication`，通过测试依赖装配运行能力，IDE 使用测试 classpath 启动它。正式包仍由标准基座加载，不携带这个测试启动入口。

测试启动类、数据库和权限配置应贴合本次验证。历史项目中的全路径匿名访问、同名类替换等本地调试做法，不应作为新项目的默认配置。

后端有两条联调路径：

- **本地启动**：IDE 调试测试入口，加载指定的应用元数据目录，并使用本地前端基座访问它。
- **本地基座容器**：把扩展和元数据装配进本机标准基座，使用 JDWP 连接基座 JVM，见 [本地基座容器调试](../local-runtime-container-debugging)。
- **平台测试实例**：用 IDEA 插件构建、上传并重启目标实例，再附加调试器，见 [平台测试实例调试](../local-ide-and-platform-debugging)。

## 开发与接入前端

前端工程分别构建，按其职责配置微前端、登录页或组件库。注册名称、入口路径、UI 模型引用及实际包名必须对应；操作方式见 [前端开发](../frontend-extension-paths)。

本地开发时，用前端基座代理 API，再把选定的微前端资源路径映射到其开发服务器。这样可以保留宿主的登录、导航和权限上下文。调试期间无需反复把开发服务器内容打成 ZIP 覆盖部署目录。

## 构建应用交付包

在流水线的临时装配目录中，把后端产物放入 `metadata/extend/`，把前端包放入 `metadata/micro-web/package/`，再打包整个 `metadata/`，形成以下交付结构：

```text
metadata/
├── app.metadata.json
├── business-model/
├── logic-flow/
├── ui-model/
├── ui-schema/
├── extend/
│   ├── myapp-service.jar
│   └── ...                       # 基座未提供且确实需要的运行依赖
└── micro-web/
    └── package/
        └── business.zip
```

构建按以下顺序进行：

1. 固定聚合仓库和各子工程提交，记录目标基座的标签与 digest。
2. 运行后端测试，生成扩展 JAR，按目标基座的 runtime manifest 过滤依赖。
3. 构建前端包，核对包内入口和平台中的微前端注册。
4. 将模型、扩展 JAR、保留依赖和前端包装配到本次构建的干净目录。
5. 保存配套版本清单，生成应用交付包。

使用现有项目时，沿用它的正式装配脚本和流水线。由流水线生成的部署产物，无需在日常开发中手工替换。

## 放入标准运行基座

标准 `ouroboros-mothership` 镜像使用以下运行位置：

| 位置 | 用途 |
| --- | --- |
| `/app/base/` | 镜像内的基座程序与前端资源 |
| `/app/metadata/` | 当前应用元数据，包含应用级 `extend/` |
| `/app/deploy/metadata/` | 外部部署的应用元数据；镜像没有内置元数据时，初始化脚本将其链接为 `/app/metadata/` |
| `/app/deploy/application.yml` | 部署环境配置 |
| `/app/deploy/instance.yml` | 实例配置 |
| `/app/deploy/logs/`、`/app/deploy/workspace/` | 日志与运行工作目录 |

`/app/deploy/extend/` 是另一个受启用条件控制的部署级扩展目录。应用包中的 JAR 通常进入应用自己的 `metadata/extend/`，不要把两个目录混为一谈。

应用资产可以随镜像内置，也可以作为部署目录挂载。两种来源会影响部署级扩展的默认启用状态，部署时应核对实际使用的初始化与启动脚本。环境连接、数据库初始化和更新操作见 [应用发布与回滚](../../operations/application-release-and-rollback)。

## 检查一组版本是否可以交付

用正式基座启动装配后的应用包，再检查业务入口。只在本地测试启动类中通过，无法覆盖镜像内的依赖和资源加载差异。

交付记录至少包含基座 digest、应用元数据提交、后端扩展版本、额外依赖及前端包版本。多仓项目再保存各子模块提交。回退时按这一组版本恢复，并单独处理数据库和现场配置的兼容性。

## 常见问题

### 多仓聚合是不是这种模式的必要条件？

不是。单仓也可以构建标准基座加载的应用；多仓项目同样可以拥有自己的启动模块。运行模式与仓库组织分别选择。

### 本地调试通过，部署后为什么找不到 Service 或模型？

先确认扩展 JAR 和额外依赖已经进入实际加载目录，再检查自动配置、SPI 和 JAR 内资源。测试 classpath 中存在、但正式交付包中缺失的依赖，是常见原因。

### 基座与扩展出现同名异版本依赖，能直接把它们都放进去吗？

先用 runtime manifest 和依赖过滤报告找出差异，再统一版本或验证兼容性。过滤插件遇到异版本默认保留并提示，需要开发者进一步处理，不能据此判断两份依赖可以安全共存。
