# 模块模型

模块模型组织应用中的功能入口。一棵模块树把已有菜单和权限按使用者熟悉的方式编排起来：哪些入口归为一组、分组叫什么、先显示什么，都可以在这里调整。业务字段、页面内容和接口处理仍保留在各自的模型中。

## 模块怎样形成

应用中的原始模块来自业务模型投影、程序菜单投影和模块定义。点分全名提供默认层级，例如 `settings.profile` 默认位于 `settings` 下；显式指定 `parent` 可以改变归属而保持模块标识不变。程序菜单投影还会补齐缺少的父模块，供后续编排使用。

开发平台的模块编排在原始结构上保存一组差异。运行时把差异应用到模块集合，再据此编排菜单和权限。这样可以为交付项目调整导航，又保留基座或插件提供的原始功能定义。

## 模块、菜单与权限怎样配合

### 选择和编排菜单

模块的 `menu` 引用一个主菜单，`subMenus` 引用其他入口。编排时保留原菜单的标识、目标地址、打开方式和使用范围，调整它在导航中的父级、标题、图标与顺序。主菜单挂在模块的父级下，子菜单挂在模块自身下面。

主菜单引用找不到实际菜单时，集成器可以为模块建立没有地址的分组占位；子菜单引用找不到时则不会成为有效入口。最终用户看到的导航，还要经过菜单区域选择、权限过滤与空分组清理。

### 组织权限树

模块的 `authorities` 引用已有权限项。编排保留真实权限所关联的接口、页面、菜单和数据访问控制定义；调整模块位置不会替用户授予新的业务权限。

没有引用权限的模块可以形成用于组织树结构的占位权限，缺少的祖先也会被补齐。这些分组有助于展示和定位，不能当作包含所有子权限的授权。

## 用差异调整应用结构

例如，将已有模块 `settings.profile` 移到 `workspace` 下并改名：

```json
[
  {
    "diffType": "modify",
    "fullName": "settings.profile",
    "parent": "workspace",
    "title": "个人设置",
    "order": 20
  }
]
```

这里修改的是模块归属与显示信息。原菜单的 URL、页面实现以及业务接口保持原有定义。`workspace` 应是最终模块集合中的有效父模块。

差异按列表依次应用：`add` 加入模块，`remove` 从编排集合移除模块，`modify` 修改已存在的模块。`modify` 的标量属性未提供时沿用原值；主菜单还要求提供非空白引用。`subMenus`、`authorities` 提供非空列表时整体替换原列表，空列表会沿用原列表，不能据此清空引用。

## 核心属性

| 属性 | 作用 | 说明 |
| --- | --- | --- |
| `fullName` | 模块全名 | 模块树中的稳定标识，点号表达名称层次。 |
| `name` | 模块名称 | 由全名末段计算得到的只读名称。 |
| `parent` | 上级模块 | 指定父模块；未显式指定时可从全名推导。 |
| `title` | 模块标题 | 导航和管理界面中的显示名称。 |
| `description` | 模块说明 | 解释模块的业务职责。 |
| `icon` | 模块图标 | 用于模块入口和导航。 |
| `order` | 展示顺序 | 决定同级模块的排序。 |
| `menu` | 主菜单引用 | 引用该模块的主菜单。 |
| `subMenus` | 子菜单引用 | 按菜单全名引用纳入模块的入口。 |
| `authorities` | 权限引用 | 列出纳入模块的权限项标识。 |

### 模块树重组定义

`modules-diff` 保存的是模块变更项集合。每条变更分别声明目标和需要调整的属性。

| 属性 | 作用 | 说明 |
| --- | --- | --- |
| `diffType` | 变更类型 | `add` 新增模块，`remove` 删除模块，`modify` 修改模块。 |
| `fullName` | 目标模块 | 标识这条变更针对的模块。 |
| `parent` | 目标父模块 | 在重组时调整模块的父级位置。 |
| `title` | 标题覆盖 | 修改模块显示名称。 |
| `description` | 说明覆盖 | 修改模块职责说明。 |
| `icon` | 图标覆盖 | 修改模块入口图标。 |
| `order` | 顺序覆盖 | 修改同级排序。 |
| `menu` | 主菜单覆盖 | 修改模块引用的主菜单。 |
| `subMenus` | 子菜单调整 | 非空列表整体替换原引用，空列表沿用原值。 |
| `authorities` | 权限调整 | 非空列表整体替换原引用，空列表沿用原值。 |


## 编排时需要保留什么

模块的全名是其他定义的引用依据。只是调整展示名称时修改 `title`，只是换位置时修改 `parent` 和 `order`，无需重命名原菜单或页面。父级调整应避免循环，菜单与权限引用应指向实际存在的定义。

在模块编排中隐藏入口，只影响编排结果。底层业务模型、页面和接口仍然存在；需要限制使用时还应调整相应权限。模块树和权限树也不要求每个节点一一对应：一个模块可以收纳多个权限，不直接对应页面的能力也可以保留权限定义。

## 常见问题

### 为什么模块存在，导航里却没有？

检查模块有没有有效主菜单或子菜单、菜单是否位于当前导航区域，以及当前用户是否拥有对应菜单权限。没有地址且没有可见子项的分组会被清理。

### 从模块树移除功能会删除业务数据吗？

不会。模块差异移除的是功能编排中的节点，业务模型和数据的删除属于其他操作。

### 修改标题后，页面地址需要一起修改吗？

不需要。模块标题用于编排展示，菜单 URL 和 UI 模型路由是独立标识。
