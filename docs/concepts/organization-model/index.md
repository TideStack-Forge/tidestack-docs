# 组织模型

组织模型描述公司、部门、岗位、员工和任职关系。这些对象提供人员归属与职责信息，供业务字段选择、审批候选人解析和数据范围控制使用。登录账号与员工分别管理，通过人员主体关联起来。

## 组织结构怎样连接人员

公司和部门构成结构层级，实际岗位挂在组织节点下，员工通过任职记录关联岗位。一名员工可以有主岗、兼职或代理任职；同一个岗位也可以有多名任职人员。

| 对象 | 回答的问题 | 主要关联 |
| --- | --- | --- |
| 公司、部门 | 组织单位怎样分层 | 上级节点与负责人。 |
| 岗位定义 | 可复用的岗位类别是什么 | 岗位编码、名称和级别。 |
| 实际岗位 | 这个组织单位设有什么岗位 | 所属组织、岗位类别与编制。 |
| 员工 | 这个人是谁 | 人员资料与登录用户。 |
| 任职 | 谁在什么时间担任什么岗位 | 员工、实际岗位、任职类型和日期。 |

例如“负责人”可以是一个可复用岗位类别，两个部门分别设置自己的负责人岗位，再由不同员工担任。不能将岗位类别编码当成实际岗位 ID，也不能将员工 ID 当成登录用户 ID。

## 结构层级与行政级别

`parent` 表达实际父子关系，`adminLevel` 表达行政级别，两者分别维护。一个节点位于树的第三层，并不自然等于某个行政级别；增加展示分组也不应随意改变行政含义。

组织节点还区分结构性和职能性：公司、部门构成骨架，岗位属于职能节点。展示组织树时可以按用途选择是否展开岗位，不必为隐藏岗位改变真实组织关系。

部门的 `parentDepartmentDetail` 仅在上级是部门时返回对象，直属公司时为空；`companyDetail` 提供所属公司。这些都是解析结果，无需作为另一组独立外键重复保存。

## 岗位类别与实际岗位

岗位定义通过 `key` 提供可复用名称、级别和职责说明。实际岗位的 `positionKey` 引用它，运行时优先使用有效定义中的名称、级别和说明；编制、所属组织与负责人仍由实际岗位自己保存。

因此，更新岗位定义可能影响多个实际岗位的展示和语义。只调整一个部门的编制，应修改该部门的实际岗位；调整整个岗位类别的职责，才修改公共岗位定义。

## 任职如何影响部门与公司

任职的开始、结束日期参与有效性判断：尚未到开始日期或已经超过结束日期的任职不属于当前任职，结束日期当天仍有效。没有结束日期表示未设置任职终点。

员工的主岗位来自当前有效的 `PRIMARY` 任职。运行时沿该岗位向上查找部门和公司，形成组织上下文。缺少有效主岗时，相关部门、公司详情可能为空；不应靠修改页面上的显示值来补造组织归属。

员工对象中的 `department` 是从主岗位父节点得到的便捷标识。如果岗位层级较复杂，需要部门对象时应使用 `departmentDetail` 的向上解析结果。建立任职时应保持主岗唯一，避免依赖多个主岗记录的遍历顺序。

## 核心属性

### 组织节点

| 属性 | 作用 | 说明 |
| --- | --- | --- |
| `id` | 节点标识 | 公司、部门和岗位等组织节点的唯一标识。 |
| `name` | 节点名称 | 组织树及管理界面显示的名称。 |
| `type` | 节点类型 | 区分公司、部门和岗位等节点。 |
| `parent` | 父节点 | 指定节点所属的上级组织。 |
| `leaderEmployee` | 负责人 | 引用节点负责人的员工标识。 |
| `description` | 节点说明 | 解释组织职责或补充信息。 |
| `adminLevel` | 行政级别 | 公司、部门等结构节点的行政分级，不等同于树的物理深度。 |
| `category` | 节点分类 | `STRUCTURAL` 结构节点、`FUNCTIONAL` 职能节点；由节点类型提供。 |
| `parentDetail` | 上级详情 | 根据父节点标识解析的只读对象。 |
| `leaderEmployeeDetail` | 负责人详情 | 根据负责人标识解析的只读员工对象。 |

### 岗位定义

岗位定义提供可复用的岗位类别。

| 属性 | 作用 | 说明 |
| --- | --- | --- |
| `key` | 岗位定义编码 | 预定义岗位的稳定编码。 |
| `name` | 岗位定义名称 | 预定义岗位的显示名称。 |
| `level` | 岗位层级 | 保存岗位定义的层级信息。 |
| `description` | 岗位定义说明 | 解释该岗位的职责。 |

### 实际岗位

实际岗位是组织树中的职能节点。它保存自己的 `id`、`parent`、`leaderEmployee`、名称、说明和编制，并可引用岗位定义；`type` 固定为 `position`，`category` 为 `FUNCTIONAL`。

| 属性 | 作用 | 说明 |
| --- | --- | --- |
| `positionName` | 实际岗位名称 | 解析后的岗位名称；有效岗位定义名称优先，未取得时使用实际岗位保存的名称。 |
| `positionKey` | 岗位定义引用 | 实际岗位引用的预定义岗位编码。 |
| `level` | 岗位层级 | 优先取引用的岗位定义级别，未取得时取实际岗位值。 |
| `headcount` | 岗位编制 | 实际岗位计划配置的人数。 |
| `actualCount` | 实际人数 | 运行时计算得到的实际任职人数。 |

### 员工

| 属性 | 作用 | 说明 |
| --- | --- | --- |
| `id` | 员工标识 | 组织人员的唯一标识。 |
| `name` | 员工姓名 | 人员选择和组织管理使用的名称。 |
| `gender` | 性别 | 员工的性别信息。 |
| `mobile` | 手机号 | 员工的手机联系方式。 |
| `email` | 邮箱 | 员工的电子邮箱。 |
| `birthday` | 生日 | 员工的生日信息。 |
| `type` | 人员主体类型 | 员工主体使用 `employee`。 |
| `user` | 用户关联 | 运行时解析关联登录用户的身份标识，不是员工表中的业务字段。 |
| `userDetail` | 用户详情 | 关联登录用户的只读对象。 |
| `department` | 所属部门 | 接口计算属性，返回主岗位的父节点标识；需要部门对象时使用 `departmentDetail`。 |
| `appointments` | 任职列表 | 运行时员工模型聚合当前有效任职；历史任职需通过任职查询。 |
| `currentAppointments` | 有效任职 | 按任职起止日期筛选的任职集合。 |
| `primaryAppointment` | 主岗任职 | 当前有效任职中类型为 `PRIMARY` 的记录。 |
| `primaryPosition` | 主岗位 | 由主岗任职解析的实际岗位。 |
| `departmentDetail` | 部门详情 | 沿主岗位的上级链查找部门，得到只读部门对象。 |
| `companyDetail` | 公司详情 | 沿主岗位的上级链查找公司，得到只读公司对象。 |
| `orgChain` | 组织链 | 从所属部门或公司向上遍历得到的只读节点列表。 |

### 任职关系

| 属性 | 作用 | 说明 |
| --- | --- | --- |
| `id` | 任职标识 | 唯一识别一条任职记录。 |
| `employee` | 员工引用 | 指定任职人员。 |
| `position` | 岗位引用 | 指定人员担任的实际岗位。 |
| `type` | 任职类型 | `PRIMARY` 主岗、`SECONDARY` 兼职、`ACTING` 代理。 |
| `startDate` | 开始日期 | 指定任职生效日期。 |
| `endDate` | 结束日期 | 指定任职结束日期，供有效任职判断使用。 |
| `employeeDetail` | 员工详情 | 任职关联的只读员工对象。 |
| `positionDetail` | 岗位详情 | 任职关联的只读实际岗位对象。 |
| `current` | 当前有效 | 根据起止日期计算的只读状态。 |
| `primary` | 是否主岗 | 根据任职类型计算的只读状态。 |


### 部门的派生关系

| 属性 | 含义 | 说明 |
| --- | --- | --- |
| `parentDepartmentDetail` | 上级部门 | 直属公司时为空。 |
| `companyDetail` | 所属公司 | 解析得到的只读公司对象。 |

### 运行时记录的维护信息

组织模块的持久化记录还保留以下审计与删除信息，由管理服务维护。

| 属性 | 含义 | 说明 |
| --- | --- | --- |
| `createdBy` | 创建人 | 创建该记录的操作身份。 |
| `createdAt` | 创建时间 | 记录创建时刻。 |
| `updatedBy` | 更新人 | 最近修改该记录的操作身份。 |
| `updatedAt` | 更新时间 | 记录最近修改时刻。 |
| `deletedBy` | 删除人 | 逻辑删除该记录的操作身份。 |
| `deletedAt` | 删除时间 | 记录逻辑删除时刻。 |
| `isDeleted` | 删除状态 | 逻辑删除标记。 |

## 与账号、审批和权限配合

员工表示业务人员，账号表示登录身份。账号通过员工主体建立关联后，运行时才能从当前用户找到员工及其任职；仅填写相同姓名或手机号不会建立这种关系。

组织关系为审批和数据权限提供事实。某人担任某岗位，不等于自动拥有系统中任意同名角色的权限；某部门负责人也不会自然取得所有下属业务记录的访问权。这些能力需要各自的候选规则或授权设置。

人员档案的补充字段与动态表单通过人员档案能力管理。它们可以扩展人员资料，不应替代组织节点、岗位和任职这些正式关联。

## 常见问题

### 已建员工，为什么登录后仍找不到部门？

检查账号是否关联员工主体、员工是否有当前有效主岗，以及主岗位向上是否存在有效部门。分别核对人员和用户标识，不能只按姓名匹配。

### 员工可以属于多个岗位吗？

可以，使用多条任职记录表达。主岗、兼职和代理的用途不同；依赖默认部门的功能主要取当前有效主岗。

### 岗位人数与编制为什么不同？

`headcount` 是计划编制，`actualCount` 是运行时统计结果。调整编制不会直接新增员工或建立任职。
