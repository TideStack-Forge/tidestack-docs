核心概念与模型地图

潮汐栈把应用、业务定义、数据结构、页面入口、接口契约、执行过程和治理边界分开建模，再在运行时装配成应用。模型是平台能力的稳定契约；开发菜单、编辑器和运行时服务都是这些模型的不同消费入口。

本页是模型概念的唯一总入口。要查某个模型的详细作用、属性、关系和使用入口，直接进入下面的对应页面；要查所有 metadata 文件格式，再进入 JSON Schema 参考。

应用如何形成​

业务模型是大多数业务交付的语义中心，但不是所有模型的上游：应用和模块提供容器，组织和权限提供治理，配置和字典提供运行支撑，页面、接口和流程模型分别承载自己的契约。

典型装配链路​

交付一个长期维护的业务对象​

  1. 用 应用模型 和 模块模型 确认应用边界与归属。
  2. 用 业务模型 定义对象、字段、关系和动作。
  3. 检查生成或关联的 数据模型，必要时补充 字段定义 和 数据字典模型。
  4. 用 UI 模型 暴露页面入口，用 UI Schema 模型 或标准视图实现页面。
  5. 用 WebAPI 模型 定义接口，用 逻辑流模型 承接自动处理。
  6. 用 菜单模型 组织导航，用 权限模型 限制访问。

需要人工参与的业务过程​

以业务模型作为业务数据载体，以 审批流模型 描述参与人、节点和状态；通过 组织模型 提供人员与岗位上下文，通过 权限模型 控制发起、处理和查看范围。审批前后的自动写入、通知或集成再交给逻辑流、通知和 RPC 资源。

需要接入外部系统​

先用 WebAPI 模型 定义平台自身接口边界，再用 RPC 模型 描述外部调用；短流程组合用逻辑流，复杂协议或专用 SDK 进入 融合开发。

模型与支撑资源的边界​

不是每一种 metadata 都是独立的核心模型。通知模板、定时任务、消息队列绑定、业务日志、国际化和数据初始化等资源，依附于模型或运行链路提供交付能力。它们的作用、属性、关系和 Schema 见 平台支撑资源。

不要混淆的边界​

  • 业务模型描述业务语义，数据模型描述数据结构；业务模型可以投射数据模型，但两者不是同一个对象。
  • UI 模型描述入口和实现方式，UI Schema 描述页面内容；微前端是 UI 模型的另一种实现资源。
  • 菜单模型负责导航，权限模型负责访问边界；菜单可见不等于接口和数据一定可访问。
  • 逻辑流负责机器执行，审批流负责人员参与的长流程；审批流中的自动动作可以调用逻辑流。
  • 字段定义和数据字典提供可复用值语义，但不替代业务模型。

扩展边界​

新增字段类型、表达式、脚本上下文、逻辑流节点、页面组件、微前端或处理器时，必须通过对应扩展点注册。扩展实现补充模型能力，不绕过模型、菜单、权限或运行时装配机制。
