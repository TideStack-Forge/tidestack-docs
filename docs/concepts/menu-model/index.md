# 菜单模型

菜单模型把应用中的页面组织为用户可以浏览和打开的导航入口。菜单定义入口的名称、图标、目标地址和打开方式，模块树决定这些入口如何分组、排列，权限决定当前用户能够看到哪些入口。

同一个页面可以从菜单、按钮或链接打开。调整菜单层级和标题，不需要改变页面路由；页面的内容仍由 UI Schema、微前端或其他页面实现负责。

## 从菜单定义到导航树

以“设置 / 资料设置”为例，分组与页面入口可以分别声明。

分组菜单：

```json
{
  "fullName": "settings",
  "title": "设置",
  "icon": "fa fa-cog",
  "placement": "main",
  "order": 100
}
```

页面入口菜单：

```json
{
  "fullName": "settings.profile",
  "title": "资料设置",
  "url": "/account/profile",
  "icon": "fa fa-user",
  "placement": "main",
  "showMode": "tab",
  "order": 10
}
```

两个对象分别描述分组和页面入口。按默认归属，`settings.profile` 位于 `settings` 下；`url` 指向 `/account/profile` 页面，菜单全名与页面路径不必相同。分组没有配置地址，主要用于展开下级菜单。

这些定义还要进入应用模块树，并满足当前用户的菜单授权，才能成为可见导航。运行时的形成过程是：

1. **汇总定义**：收集业务模型投影、程序或插件资源，以及扩展提供者中的菜单。
2. **模块编排**：按最终模块树选择菜单，调整父级、标题、图标和顺序。
3. **区分区域**：按 `placement` 选择主导航或次级导航中的菜单。
4. **权限过滤**：依据当前身份的有效权限，保留可见入口。
5. **组织输出**：主导航构建父子树，去掉没有地址、也没有可见子项的空分组，再交给前端展示。

因此，原始菜单集合、编排后的菜单集合和用户实际看到的导航，可能并不相同。

## 标识、层级与页面地址

### 菜单全名与默认层级

`fullName` 是菜单的稳定标识，用于模块引用、权限关联和同名定义合并。标题可以随用户习惯调整，标识应尽量保持稳定，避免连带修改其他定义中的引用。

基础菜单从全名推导简单名称与父级。例如：

| 全名 | 简单名称 | 默认父级 |
| --- | --- | --- |
| `settings` | `settings` | 无，作为根节点。 |
| `settings.profile` | `profile` | `settings`。 |
| `settings.profile.preferences` | `preferences` | `settings.profile`。 |

这个默认层级会参与模块组织。经过模块树编排后，菜单可以放到另一个父级下面，同时保留原有全名和目标地址。排查运行结果时，应以编排后的父级为准。

### 分组与可打开的入口

菜单有子项时，可以作为分组；有 `url` 时，可以打开目标页面。两者可以同时存在：当前前端会把标题点击用于打开页面，把展开按钮用于展开或收起子项。

没有地址的分组依靠可见子项保留。若子项全部被过滤，该分组也会从主导航中移除。一个没有地址、也没有子项的节点，不会作为空入口显示。

### 菜单与 UI 模型

内部页面的 `url` 通常指向 [UI 模型](../ui-model/) 的 `path`，UI 模型再选择 [UI Schema](../ui-schema/) 或[微前端](../micro-web-model/)等实现。新增菜单不会同时创建路由、页面内容或后端接口。

示例中的 `/account/profile` 必须已有可用页面。修改菜单全名不会自动修改这个地址，修改地址也不会自动迁移相关页面和权限。

## 核心属性

### 定义属性

| 属性 | 作用 | 说明 |
| --- | --- | --- |
| `fullName` | 菜单全名 | 菜单的稳定标识；点号表示默认名称层次，也是模块和权限引用的依据。 |
| `title` | 菜单标题 | 导航中显示的名称；模块编排可以覆盖最终标题。 |
| `url` | 目标地址 | 指向内部页面路由或外部地址；纯分组可以不设置。 |
| `icon` | 菜单图标 | 用于导航识别；模块编排可调整最终图标。 |
| `placement` | 导航区域 | `main`、`secondary` 或 `all`，默认 `main`；与菜单的父子层级无关。 |
| `showMode` | 打开方式 | 内部页面支持 `tab`、`fullScreen` 和 `newWindow`；未指定时前端按标签页处理。 |
| `order` | 排序值 | 默认 `0`，值越小越靠前；模块编排可以改变最终排序。 |
| `extraProps` | 扩展属性集合 | 为提供者或扩展实现保存附加属性；JSON 中按属性名平铺，不保证每个扩展属性都会由所有导航布局处理。 |

### 派生属性与树形结果

| 属性 | 作用 | 说明 |
| --- | --- | --- |
| `name` | 简单名称 | 从全名最后一段计算得到，基础定义中无需单独填写。 |
| `parent` | 父级标识 | 基础定义从全名推导，模块编排后的对象可以提供新的父级。 |
| `children` | 可见子项 | 主导航树构建后的结果，由运行时填充；不作为基础菜单资源中的嵌套定义。 |
| `scope` | 运行时导航区域 | 部分运行时视图以此名称返回导航区域；菜单资源使用 `placement` 声明。 |

菜单资源按单项声明，`children` 是组装结果。直接把子菜单写进一个对象的 `children` 中，不能替代正式的菜单定义与模块归属。

## 导航区域与打开方式

### 主导航与次级导航

`placement` 决定菜单参加哪一类导航，具体摆放位置由当前前端布局决定。

| 值 | 含义 |
| --- | --- |
| `main` | 参加主导航，按父子关系组织为树。 |
| `secondary` | 参加次级导航，由次级入口区域展示。 |
| `all` | 同时参加主导航和次级导航。 |

“次级导航”表示另一个展示区域，不表示第二级子菜单。要让“资料设置”成为“设置”的下级，应调整父子归属，而不是把 `placement` 改为 `secondary`。

同一树路径上的节点还应具有相容的导航区域。子项进入主导航、父项却只进入次级导航时，主导航中会缺少它依附的父级，不能形成预期的完整路径。

### 标签页、全屏与新窗口

| `showMode` | 内部页面的行为 |
| --- | --- |
| `tab` | 在应用标签页中打开，或切换到已打开的页面。 |
| `fullScreen` | 在当前窗口进入全屏页面模式。 |
| `newWindow` | 在新的浏览器窗口或标签中打开，实际形式取决于浏览器。 |

外部地址由前端按外部链接打开，不进入应用内部标签页。配置 `showMode` 不会改变目标页面的实现方式，也不会授予额外权限。

## 模块树如何改变菜单

[模块模型](../module-model/)通过 `menu` 引用模块的主菜单，通过 `subMenus` 引用附加菜单。运行时集成器按这些引用组织导航，而不是直接把所有原始菜单原样返回。

| 模块配置 | 对菜单的影响 |
| --- | --- |
| `menu` | 选择模块对应的主菜单，目标地址沿用被引用菜单。 |
| `subMenus` | 把引用的菜单放到该模块下面。 |
| `parent` | 调整模块主菜单的父级位置。 |
| `title` | 提供编排后菜单使用的标题。 |
| `icon` | 非空时覆盖被引用菜单的图标。 |
| `order` | 提供编排后的排序值。 |

模块需要分组入口、但找不到对应菜单时，集成器也可以提供没有地址的占位菜单。它仍需经过权限与空分组过滤，才会出现在用户导航中。

模块编排保留被引用菜单的 `fullName` 和 `url`，改变的是导航组织。程序菜单可以投影为模块并补充父级模块，业务模型也会投影相应模块；新增扩展菜单时，需要确认其模块来源和归属完整。

最终菜单标题或顺序与原始定义不同时，应先检查模块编排结果。按用户阅读顺序组织入口时，优先在[模块树编排](../../low-code/development-platform-menus/module-arrangement)中调整，无需为了移动入口修改稳定标识或路由。

## 菜单可见性与访问权限

[权限模型](../authority-model/)的 `menuItems` 关联菜单全名。下面是权限项中关联菜单的部分：

```json
{
  "menuItems": ["settings.profile"]
}
```

当前身份取得该权限后，菜单服务才能按此关联筛选入口。菜单匹配使用全名，不使用显示标题或 `url`。

对于基础点分层级，授权 `settings.profile` 会保留该项及其名称上的祖先 `settings`，使完整导航路径有机会显示。反过来，只关联父项 `settings`，不会自动授权所有子菜单。模块编排改变了实际父级时，还应检查新父级的可见性，不能只按原来的点分名称推断结果。

菜单、页面与接口分别有各自的访问目标：

| 关联 | 控制内容 |
| --- | --- |
| `menuItems` | 用户能否在导航中看到相应入口。 |
| `uiViews` | 用户能否访问相应页面。 |
| `apis` | 用户能否调用相应接口。 |

隐藏菜单不会使页面路由或接口消失。新建业务入口时，应同时核对页面与接口授权；仅在前端增加一个菜单，也不能获得后端业务操作权限。

## 菜单的定义来源

### 业务模型投影

标准业务模型在启用索引页、且未设为附属模型时，会投影相应菜单入口。菜单全名、标题、图标和顺序来自业务模型，地址指向对应标准页面。模块分组也可以提供自己的菜单。

这类入口应回到业务模型或模块编排中调整。并非每个业务模型都需要一个独立菜单，表单、详情和子表也可以由其他页面操作进入。

### 程序与插件定义

程序或插件可以用 `.menu.json` 资源声明独立菜单，每份文件保存一个菜单对象，由内置提供者加载。新的菜单来源应通过已注册的 `MenuModelProvider` 提供，并参加统一汇总、模块编排和授权过滤。

菜单汇总按全名忽略大小写合并，同一全名只保留一项，不能依靠重复声明保留两个入口。需要两个独立入口时，应使用不同全名，并分别确定模块归属和权限关联。

开发平台左侧工作区使用独立的 `dev-menu` 资源。它描述开发功能入口，与最终应用的运行态业务菜单分别维护。

### 前端运行时扩展

前端 SDK 可以动态设置徽标、增删菜单树中的项目。此类修改作用于当前前端会话，不会写回菜单资源、模块编排或角色权限；刷新后仍以正式定义下发的导航为准。

需要长期保留的导航应通过模型及其正式来源维护。徽标、临时入口和用户菜单注册的具体方法见[菜单扩展 API](../../api/frontend/sdk/menu-extension/)。

## 常见问题

### 菜单已经加载，为什么用户仍看不到？

依次检查模块树是否引用该项、父级是否完整、导航区域是否匹配，以及当前有效权限的 `menuItems` 是否关联正确全名。纯分组还需要至少一个可见子项，否则会被清理。

### 为什么只给父菜单授权，子菜单没有出现？

父项授权不等于子项授权。应在相应权限中关联需要展示的子菜单；基础点分层级中的祖先项会随已授权子项保留。

### 为什么原始菜单标题和排序没有生效？

模块编排可能覆盖最终标题、图标和顺序。先检查最终模块树，再确认运行实例已加载相应元数据。

### 为什么点击菜单没有打开预期页面？

核对 `url`、页面路由和页面权限。内部路由不可用时，前端可能尝试可打开的子入口；不要把这种回退当作目标页面已经配置成功。

### 移动菜单是否需要修改全名？

通常不需要。通过模块树调整父级与顺序，保留全名及页面地址；移动后用实际角色检查新父级、菜单、页面和接口的访问结果。
