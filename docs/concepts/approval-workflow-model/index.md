# 审批流模型

审批流模型描述由人员参与、需要等待处理的业务过程。定义说明表单、处理人、节点操作、分支条件与结束结果；运行后形成流程实例和待办任务，记录每一步由谁处理、如何流转。

## 定义、实例与任务

| 对象 | 含义 | 生命周期 |
| --- | --- | --- |
| 流程定义 | 可复用的审批规则和结构 | 设计、校验、部署和版本管理。 |
| 流程实例 | 按定义发起的一次审批 | 发起、运行、完成或其他结束状态。 |
| 待办任务 | 实例中等待人员处理的工作 | 创建、领取或分配、处理和完成。 |
| 业务表单 | 本次审批关联的数据 | 由表单适配能力读写，并受节点字段权限约束。 |

修改定义不等于修改已经运行的实例。核查审批问题时，应先确定实例使用的部署定义，再查看当前任务与历史处理记录。

## 表单与人员

### 绑定表单

`form.formType` 选择已接入的表单适配方式，`form.formId` 指定该类型下的表单。业务模型表单使用 `businessModel` 类型；实际业务对象必须存在，并满足流程发起所需的字段与规则。

业务模型提供业务数据，审批流提供等待与流转状态。审批通过后的业务变化，应通过已配置的业务衔接处理，不能把流程结束自动等同于任意业务状态已更新。

### 确定处理人

候选人可以来自指定用户、角色、岗位、发起人、表单字段，也可以要求发起时自选。候选规则引用的是不同类型的标识；员工编号、登录用户编号和岗位编号不能混用。

候选人解析为空时，审批节点可以配置自动同意、自动拒绝或转交指定用户。这个策略会直接影响业务结果，应主动设置并用真实组织数据检查。

### 控制节点字段

`permission` 按字段配置可见、可写和必填。发起、审核和办理阶段可以使用不同设置。例如审核阶段允许填写审核意见，同时将申请内容设为只读。节点字段权限和平台的接口、数据权限共同作用，不能靠隐藏表单字段替代后端授权。

## 节点与分支

| 节点类型 | 用途 | 关键配置 |
| --- | --- | --- |
| `StartNode` | 定义流程起点 | 发起阶段的表单与后续连接。 |
| `ApprovalNode` | 作出审批决定 | 单签或会签、候选人、操作、超时和无候选人策略。 |
| `HandleNode` | 交给人员办理 | 办理候选人与字段权限。 |
| `CcNode` | 将流程信息抄送给人员 | 接收人员配置。 |
| `SubflowNode` | 调用另一个审批流程 | 子流程标识、输入输出映射和驳回处理。 |
| `JoinNode` | 汇聚被激活的多个分支 | 当前稳定设计使用 `joinType: "OR"`。 |
| `EndNode` | 定义结束结果 | `approved` 或 `rejected`。 |

当前图结构通过 `edges` 表达连接。一个节点有多条出边时形成分支；没有下游汇聚节点时按互斥分支理解，通过条件和顺序选择路径。显式 OR 汇聚节点界定多分支组，并等待其中所有被激活的分支完成。不要通过把节点画在同一列、或单纯去掉条件来推断并行语义。

例如，下面是一段绑定已有业务模型的单签流程。节点之间通过 ID 连接，审批节点的候选人来自发起人：

```json
{
  "formatVersion": 1,
  "name": "sampleApproval",
  "title": "示例审批",
  "version": 1,
  "enabled": true,
  "form": { "formType": "businessModel", "formId": "sample" },
  "nodes": [
    { "id": "start", "type": "StartNode", "name": "发起" },
    {
      "id": "review", "type": "ApprovalNode", "name": "审核", "subType": "单签",
      "candidates": [{ "type": "Starter", "isChecked": true }],
      "noCandidateMode": "rejected"
    },
    { "id": "end", "type": "EndNode", "name": "结束", "outcome": "approved" }
  ],
  "edges": [
    { "id": "e1", "type": "SEQUENCE", "sourceId": "start", "targetId": "review" },
    { "id": "e2", "type": "SEQUENCE", "sourceId": "review", "targetId": "end" }
  ]
}
```

这是一份结构示例，需要先存在可绑定的 `sample` 业务模型并完成部署，不能仅凭这段 JSON 判断已能发起。实际应用通常按职责选择独立审批人，应把自审规则、无候选人规则与组织数据一起核对。

### 单签、会签与超时

单签和会签都使用 `ApprovalNode`，通过 `subType` 区分。会签还配置顺序或并行方式、通过比例与驳回操作。参与人数变化会影响通过比例对应的实际票数，应结合候选人解析结果核对。

超时配置描述等待期限和到期操作。超时转交需要有效目标人，提醒消息则依赖通知模板及渠道配置。流程定义中的通知开关不能代替渠道连接和接收人数据。

## 保存以后何时能够发起

1. **保存设计**：开发平台保存静态审批流定义及画布布局。
2. **加载元数据**：将定义交付给目标应用并刷新，形成可识别的流程模型。
3. **部署定义**：显式部署到审批引擎，得到可运行的部署版本。
4. **发起实例**：根据已部署定义提交业务表单和本次所需人员信息。
5. **处理待办**：按节点规则办理，查看流转和处理记录。

静态定义的 `formatVersion` 当前为 `1`；平台会将其转换为运行图。它与 `version` 以及引擎部署版本用途不同，不要通过手工改格式版本来升级审批业务版本。

## 核心属性

| 属性 | 作用 | 说明 |
| --- | --- | --- |
| `formatVersion` | 元数据格式版本 | 静态元数据当前为整数 `1`；与运行图格式和业务版本分别管理。 |
| `name` | 流程标识 | 应用加载和引用流程时使用的名称。 |
| `title` | 流程标题 | 设计器和管理页面中的显示名称。 |
| `description` | 流程说明 | 解释流程用途及适用条件。 |
| `version` | 流程版本 | 关联流程定义的部署和历史实例。 |
| `enabled` | 启用状态 | 控制定义是否启用。 |
| `form` | 表单绑定 | 指定业务表单的类型和标识。 |
| `notification` | 通知配置 | 配置流程通知，由通知能力完成投递。 |
| `nodes` | 节点集合 | 保存开始、审批、办理、抄送、子流程、汇聚和结束等节点。 |
| `edges` | 连接集合 | 保存节点流转、条件和顺序。 |
| `editorLayout` | 编辑布局 | 保存画布位置等设计态信息。 |

### 表单与节点

| 属性 | 作用 | 说明 |
| --- | --- | --- |
| `form.formType` | 表单类型 | 选择业务模型表单或其他已接入的表单适配方式。 |
| `form.formId` | 表单标识 | 引用该类型下的具体表单。 |
| `nodes[].id` | 节点标识 | 连线引用的唯一节点编号。 |
| `nodes[].type` | 节点类型 | 决定节点的处理方式和可用配置。 |
| `nodes[].name` | 节点名称 | 设计器和审批过程中的显示名称。 |
| `nodes[].candidates` | 候选人配置 | 定义参与处理的人员或组织解析规则。 |
| `nodes[].permission` | 字段权限 | 配置该节点对表单字段的访问权限。 |
| `nodes[].notify` | 节点通知 | 控制是否启用节点通知。 |
| `edges[].id` | 连线标识 | 唯一识别一条连接。 |
| `edges[].type` | 连线类型 | 当前稳定图契约使用 `SEQUENCE`，分支由出边和条件表达。 |
| `edges[].sourceId` | 来源节点 | 引用连线起点。 |
| `edges[].targetId` | 目标节点 | 引用连线终点。 |
| `edges[].condition` | 流转条件 | 指定条件分支采用的判断规则。 |
| `edges[].order` | 判断顺序 | 控制有顺序要求的分支判断。 |

### 节点字段权限

以下属性属于 `nodes[].permission[]` 中的一项字段权限。

| 属性 | 作用 | 说明 |
| --- | --- | --- |
| `name` | 字段名称 | 指定受控的表单字段。 |
| `label` | 字段标题 | 在权限配置中显示字段的名称。 |
| `visible` | 允许查看 | 控制该节点是否显示字段。 |
| `writable` | 允许编辑 | 控制该节点是否可以修改字段。 |
| `required` | 必填要求 | 控制该节点提交时是否必须提供字段值。 |

### 流程通知

| 属性 | 作用 | 说明 |
| --- | --- | --- |
| `notification.taskCreatedTemplate` | 待办通知模板 | 新任务创建时使用的通知模板。 |
| `notification.taskTimeoutRemindTemplate` | 超时提醒模板 | 任务超时提醒使用的通知模板。 |
| `notification.instanceCompletedTemplate` | 完成通知模板 | 流程完成时使用的通知模板。 |
| `notification.instanceRejectedTemplate` | 驳回通知模板 | 流程驳回时使用的通知模板。 |


### 审批节点专有属性

以下字段位于 `nodes[]` 中的 `ApprovalNode`；超时属性位于它的 `timeout` 中。

| 属性 | 含义 | 说明 |
| --- | --- | --- |
| `subType` | 审批方式 | `单签` 或 `会签`。 |
| `actions` | 可用操作 | 该节点允许的审批操作标识。 |
| `noCandidateMode` | 无候选人处理 | `approved`、`rejected` 或 `reAssignUser`。 |
| `reAssignUsers` | 转交用户 | 无候选人且采用转交策略时使用。 |
| `allowRejectToSelf` | 允许驳回自身 | 默认允许，由审批操作规则消费。 |
| `timeout` | 超时设置 | 到期时间和处理策略。 |
| `timeout.duration` | 等待期限 | 超时持续时间定义，由引擎解释。 |
| `timeout.action` | 到期操作 | 选择超时后的处理动作。 |
| `timeout.transferTo` | 转交目标 | 超时转交时的用户标识。 |
| `multipleMode` | 会签执行方式 | 会签使用，缺省为 `并行`。 |
| `percentage` | 会签通过比例 | 会签使用，缺省为 100。 |
| `rejectAction` | 会签驳回操作 | 会签使用，缺省为 `reject`。 |

### 子流程、汇聚和结束节点

| 属性 | 适用节点 | 说明 |
| --- | --- | --- |
| `subFlowKey` | 子流程 | 引用子流程的定义标识。 |
| `rejectAction` | 子流程 | 指定子流程拒绝后的处理规则。 |
| `inParameters` | 子流程 | 父流程向子流程的输入映射。 |
| `outParameters` | 子流程 | 子流程向父流程的输出映射。 |
| `inParameters[].source` | 子流程输入 | 来源变量。 |
| `inParameters[].expression` | 子流程输入 | 来源值的计算表达式。 |
| `inParameters[].target` | 子流程输入 | 子流程目标变量。 |
| `outParameters[].source` | 子流程输出 | 子流程来源变量。 |
| `outParameters[].expression` | 子流程输出 | 输出值的计算表达式。 |
| `outParameters[].target` | 子流程输出 | 父流程目标变量。 |
| `joinType` | 汇聚 | 当前稳定值为 `OR`，不能将预留的 AND 视为可用设计能力。 |
| `outcome` | 结束 | `approved` 或 `rejected`，未指定时采用 `approved`。 |

### 候选人属性

每个候选人对象都有 `type`，其他属性由类型决定。

| 属性 | 适用类型 | 说明 |
| --- | --- | --- |
| `type` | 全部 | `User`、`Role`、`Position`、`UserSelect`、`Starter`、`FormField`。 |
| `users` | `User` | 指定用户标识列表。 |
| `roles` | `Role` | 角色标识列表。 |
| `positions` | `Position` | 岗位标识列表。 |
| `mode` | `UserSelect` | `single` 单选、`multiple` 多选。 |
| `allowOverride` | `UserSelect` | 是否允许发起人覆盖该节点审批人，缺省为 false。 |
| `candidateRange` | `UserSelect` | 范围类型预留字段；当前未完成成员资格数据源校验，不能当作已生效的选人限制。 |
| `isChecked` | `Starter` | 发起人候选配置。 |
| `field` | `FormField` | 提供候选人的表单字段名。 |

### 连接条件

`edges[].condition` 可以是比较条件，也可以是组合条件；条件内容是结构化对象，不是任意字符串。

| 属性 | 条件类型 | 说明 |
| --- | --- | --- |
| `left` | 比较 | 比较左侧字段描述。 |
| `left.field` | 比较 | 参与判断的字段或变量。 |
| `left.type` | 比较 | 左值的类型描述，设计时应与右值类型对齐。 |
| `op` | 比较 | 比较操作符。 |
| `right` | 比较 | 比较右侧的实际值，字符串值无需自行再加一层引号。 |
| `conjunction` | 组合 | `or` 为或，其他值按与处理。 |
| `children` | 组合 | 可继续嵌套比较或组合条件。 |

## 常见问题

### 已保存流程，为什么发起时找不到？

依次核对目标应用是否已加载定义、流程是否启用、是否显式部署成功，以及发起时引用的定义标识。画布保存成功不代表引擎已有可运行版本。

### 配了角色或岗位，为什么没有审批人？

检查引用标识、角色成员或岗位任职、员工与登录用户的关联，以及当前候选解析器的能力。再检查无候选人策略，避免将解析错误误当作正常自动通过。

### 审批流可以代替逻辑流处理所有自动任务吗？

审批流负责人员等待、待办和审批状态；逻辑流负责机器执行。即时计算、数据处理和外部调用宜放在逻辑流或业务动作中，再通过对应适配与审批过程衔接。
