平台支撑资源

平台支撑资源把运行链路需要的公共定义放在合适的位置：开发平台需要导航和编辑器元数据，逻辑流需要节点目录，集成能力需要凭据、消息与调度，运维链路需要日志、初始化和错误码。它们各自服务一个明确的消费者，不承担业务模型的对象、关系和动作。

先确定资源服务谁​

同名的“定义”可能处于不同链路。开发菜单服务的是开发工作区，菜单模型服务的是应用导航；逻辑流节点定义描述编辑器如何创建节点，节点实现才负责执行；计划任务定义描述周期触发，延迟任务则由运行时调度接口提交。

资源进入应用后通常经历三个阶段：文件或管理入口提交定义，专用 provider 发现并解析，运行时服务把它交给页面、逻辑流、接口或运维能力消费。某一阶段成功不代表后续阶段已经完成，例如保存计划任务不等于调度器已经注册，上传微前端包也不等于菜单已经出现。

开发工具定义​

开发菜单​

开发菜单定义开发平台的功能入口，与应用运行态菜单分别管理。stage 决定欢迎阶段或应用开发阶段，placement 决定放在主导航还是辅助区域。它不会成为用户应用的业务菜单。契约：dev-menu.schema.json。

属性作用说明
fullName菜单标识唯一识别开发菜单。
title菜单标题开发平台导航中显示的名称。
url跳转地址指定开发工具或管理页面的入口。
icon菜单图标用于导航识别。
placement放置区域main 为主导航，secondary 为次级导航，all 表示两者。
stage展示阶段welcome 为欢迎页，dev 为应用开发阶段，all 表示两个阶段均展示。
showMode打开方式指定入口的展示方式。
order展示顺序控制同级菜单排序。
children子菜单嵌套组织下级开发入口。
extraProps扩展属性保存导航使用的附加信息，JSON 中按属性名展开。

逻辑流节点定义​

节点定义是编辑器和运行时之间的共同契约：编辑器据此显示节点、生成属性表单、限制端口连接；运行时再根据 type 通过节点工厂找到已注册的节点构建器和执行实现。修改节点定义的属性名称会影响已保存逻辑流，新增节点类型必须同时有执行实现。契约：flow-node.schema.json。

属性作用说明
type节点类型与运行时节点实现对应的类型标识。
label节点标题节点面板和画布中的显示名称。
icon节点图标节点的视觉标识。
iconBg图标背景指定图标背景色。
iconColor图标颜色指定图标前景色。
group节点分组组织节点选择面板。
shape节点形状指定画布上的节点形态。
description节点说明解释节点用途。
isTerminal终结节点标记声明该节点是否具有终结语义。
terminalKind终结类型区分具体的终结语义。
editorCapabilities编辑器能力声明编辑器对该节点提供的交互能力。
scaffold初始结构提供新建节点时的配置骨架。
portRules端口规则定义端口的数量、类型及连接约束。
properties属性编辑项描述节点参数的编辑表单。
svgs矢量资源提供节点使用的 SVG 资源。
order展示顺序控制节点在选择列表中的排序。

集成、通知与调度​

RPC 认证定义​

RPC 定义通过凭据名称引用认证资源。认证类型决定如何把参数应用到请求；认证资源只保存给对应构建器消费的参数，RPC 模型保存引用名称。契约：rpc-auth.schema.json。

属性作用说明
name凭据标识供 RPC 定义引用的稳定名称。
title凭据标题管理界面显示的名称。
type认证类型选择对应的凭据实现。
description凭据说明解释用途及所接入系统。
isEnabled启用状态控制该认证定义是否启用。
extraProps认证参数保存认证类型要求的专有参数，JSON 中按属性名展开。

凭据名称应保持稳定，实际认证参数按目标环境维护。停用或替换一份共享凭据前，先检查所有引用它的 RPC；不要将认证参数复制到多个逻辑流节点中。不同认证类型有自己的专有属性，需按对应实现配置。

通知模板​

通知模板声明负载和渠道内容。通知服务负责解析接收人、选择渠道和投递；模板本身不产生审批任务，也不会替代消息队列。契约：notification.schema.json。

属性作用说明
name模板标识发送通知时引用的名称。
title模板标题管理界面中的显示名称。
isEnabled启用状态控制模板是否可用。
payloadSchema负载结构约束发送通知需要提供的数据。
channel渠道配置按渠道标识保存内容模板和渠道所需参数。

发送时由调用方提供模板名称、接收对象和负载。模板内的字段引用应与 payloadSchema 和实际负载一致；渠道名称、内容格式和参数由已接入渠道解释。出现“模板可查到但未收到通知”时，还要检查接收人解析、渠道配置与投递记录。

消息队列绑定​

绑定定义连接消息队列与应用。生产绑定描述消息写向哪里，消费绑定描述从哪里接收，并可将消息交给指定逻辑流。消费组、广播和路由键会改变投递语义，不能只改 destination 就认为是同一条通道。契约：mq.schema.json。

属性作用说明
bindingType绑定类型区分生产与消费等绑定方式。
bindingName绑定标识应用内识别消息通道的名称。
destination消息目标指定消息主题或相应目标，由中间件适配器解释。
binder绑定器选择已配置的消息中间件绑定器。
group消费组定义消费者所属的分组。
contentType内容类型声明消息内容的媒体类型。
broadcast广播标记声明是否采用广播方式。
routingKey路由键提供消息路由使用的键。
flowName消费逻辑流指定消息到达后执行的逻辑流。
description绑定说明解释通道的用途。
extraProps扩展配置保存具体消息中间件所需的附加参数，JSON 中按属性名平铺。

消费绑定示例：

{
  "bindingType": "consumer",
  "bindingName": "eventConsumer",
  "destination": "business.events",
  "group": "application",
  "contentType": "application/json",
  "flowName": "consumeEvent"
}

使用前需配置可用的消息绑定器，并提供 consumeEvent 逻辑流。当前逻辑流消费者把可转换为对象的消息体放入 payload，消息头放入 headers；消费逻辑应按这两个上下文入口读取数据。消息投递与业务处理不是同一个事务，业务逻辑应处理重复消息，失败后的重投策略则要按实际绑定器核对。

计划任务定义​

计划任务按 Cron 表达式周期触发逻辑流。它描述可重复注册的周期任务；一次性延迟任务由运行时调度服务按提交时的到期时间管理，不使用这份定义。契约：schedule.schema.json。

属性作用说明
name任务标识注册和管理计划任务使用的名称。
description任务说明解释定期处理的用途。
cron触发表达式指定周期执行时间。
flowName目标逻辑流指定任务触发时执行的逻辑流。
data任务数据提供逻辑流执行需要的上下文数据。

例如，下面的周期任务在每天凌晨 2 点调用已有逻辑流：

{
  "name": "dailySummary",
  "description": "每日汇总",
  "cron": "0 0 2 * * ?",
  "flowName": "dailySummary",
  "data": { "source": "scheduler" }
}

这要求逻辑流已经存在。调度实现使用 Quartz 时，Cron 应遵循 Quartz 语法；任务的 data 作为本次逻辑流上下文传入。周期执行可能重复或失败，业务处理应考虑幂等性，并保留可定位任务名和执行结果的日志。

一次性延迟任务则调用 Scheduler.scheduleOnce，按指定时间或延迟时长触发，也可以按任务名称取消。它适合在业务运行期间安排后续工作，不需要给每个业务事件新增一份周期任务文件。

日志与数据准备​

业务日志模板​

业务日志模板按请求方法和 URL 匹配操作，再提取业务键和摘要。响应体是否保存、哪些字段脱敏，都在模板中明确；日志模板不是权限审计规则的替代品。契约：business-log.schema.json。

属性作用说明
name模板标识唯一识别日志模板。
httpMethod请求方法限定该模板匹配的 HTTP 方法。
url匹配地址限定需要记录的请求地址。
moduleName所属模块标明操作归属的业务模块。
operation操作名称标识被记录的业务操作。
level日志级别指定记录采用的级别。
businessKeyName业务键名称指定用于关联业务记录的键。
summaryTemplate摘要模板根据操作上下文生成日志摘要。
sensitiveFields敏感字段列出需要按日志规则保护的字段。
shouldSaveResponseBody保存响应体控制是否记录响应正文。

业务键应能定位被操作的业务记录，摘要应让维护人员看懂发生了什么。响应体可能很大，也可能包含敏感数据，只有确有追溯需要时才保存，并同步核对脱敏字段。模板命中了请求不表示操作成功，分析日志时还应结合结果和异常。

数据初始化定义​

初始化计划把一批基座或应用初始记录分成多个数据块。每个数据块指定目标模型、版本、匹配字段和记录，初始化执行器据此判断记录是否已经存在。计划至少包含一个 block；它不是业务导入任务的通用替代品。契约：data-init.schema.json。

属性作用说明
id计划标识唯一识别初始化计划。
version计划版本记录初始化内容版本，未指定时使用默认版本。
blocks数据块集合保存各个目标模型的初始化定义，至少包含一个数据块。
blocks[].id数据块标识在计划内识别数据块。
blocks[].targetModel目标模型引用需要初始化的数据模型。
blocks[].version数据块版本记录该数据块的内容版本。
blocks[].matchFields匹配字段用于判断目标记录是否已经存在。
blocks[].records初始记录列出需要补齐的记录数据。
{
  "id": "application.defaults",
  "version": "1",
  "blocks": [
    {
      "id": "defaults",
      "targetModel": "sample",
      "matchFields": ["code"],
      "records": [{ "code": "default", "title": "默认项" }]
    }
  ]
}

示例要求 sample 数据模型已存在，并有相应字段。matchFields 不可为空，每条记录必须包含所有匹配字段；这些字段共同用于查找已有记录。当前执行器找到记录后跳过，只插入缺失记录，不会用定义中的新内容覆盖已有记录。

数据块未指定版本时使用计划版本；执行台账记录计划、数据块、目标模型、版本和内容摘要。增加版本不等于强制覆盖业务数据，需要更新已有记录的业务迁移应使用相应迁移方案。

公共文案与结构定义​

国际化语言包​

语言包按 locale 保存页面和公共能力使用的文案。messages 是分组键到翻译文本的映射，语言包启用后才能被查找；它不会自动翻译业务数据内容。契约：i18n.schema.json。

属性作用说明
locale语言标识指定语言与地区，例如 zh-CN。
name语言名称语言选择与管理界面中的显示名称。
version资源版本记录语言包的版本。
enabled启用状态控制语言包是否启用。
isDefault默认语言声明是否作为默认语言。
direction排版方向声明从左向右或从右向左的文字方向。
timestamp资源时间记录语言包的时间信息。
messages文案映射先按文案分组，再按文案键保存翻译文本。

例如，菜单翻译按 menu 分组组织：

{
  "locale": "en-US",
  "name": "English",
  "version": "1.0.0",
  "enabled": true,
  "isDefault": false,
  "direction": "LTR",
  "messages": {
    "menu": { "settings.title": "Settings" }
  }
}

这里的键应对应平台实际消费的文案路径。修改标题不会自动重命名翻译键；缺少翻译时的显示由具体消费能力决定，不应靠同一个键保存含义不同的文本。

岗位定义​

岗位定义声明可复用的岗位类别；组织树中的实际岗位另行记录编制、负责人和任职。修改定义会影响引用该岗位类别的实际岗位显示，具体任职仍在组织模型中维护。契约：position.schema.json。

属性作用说明
key岗位编码引用预定义岗位的稳定标识。
name岗位名称岗位类别的显示名称。
level岗位层级保存岗位的分级信息。
description岗位说明解释岗位职责。

错误码定义​

错误码把稳定标识、业务编码和提示模板组织在一起。文件内容是定义数组；调用方应依赖稳定 code 或 bizCode，不要把提示文本当作程序分支条件。契约：error-code.schema.json。

属性作用说明
code错误编号错误的数值标识。
title错误标题便于识别错误类别的简短名称。
defaultMessageTemplate默认提示模板在没有其他文案覆盖时生成错误提示。
bizCode业务错误编码提供面向业务或外部调用方的错误标识。
category错误分类按用途组织错误定义。
description错误说明解释原因及适用条件。
enabled启用状态控制错误定义是否启用。

模块树重组定义​

模块树 Diff 保存新增、删除和修改模块的变更项。文件内容为变更数组，运行时应用到原始模块后再编排菜单和权限。它调整应用结构，不删除业务模型、页面或数据。契约：modules-diff.schema.json。

属性作用说明
diffType变更类型指定 add、remove 或 modify。
fullName目标模块引用需要变更的模块全名。
parent目标父模块指定重组后的父级位置。
title模块标题提供需要覆盖的显示名称。
description模块说明提供需要覆盖的职责说明。
icon模块图标提供需要覆盖的图标。
order展示顺序提供需要覆盖的同级排序。
menu主菜单引用指定调整后的主菜单。
subMenus子菜单引用修改时非空列表整体替换，空列表沿用原值。
authorities权限引用修改时非空列表整体替换，空列表沿用原值。

资源怎样进入运行链路​

  1. 提交：资源可以来自应用资源目录、JAR 内嵌 metadata 或管理界面。不同资源使用各自的文件后缀和目录。
  2. 解析：provider 读取定义并转换为对应的模型；解析失败时应查看资源诊断，不要用一份相似 JSON 代替正式契约。
  3. 注册：registry、provider 或 runtime service 建立运行时索引。刷新元数据后，旧缓存是否失效取决于具体资源服务。
  4. 消费：页面、编辑器、逻辑流、接口、调度器或日志服务按自己的契约消费资源。
  5. 验证结果：检查真正的消费方是否已发现资源，例如逻辑流节点能否执行、计划任务是否已注册、消息消费是否能触发目标逻辑流。

资源的发现、校验和运行时注册必须使用各模块的正式扩展点。不要在业务模型或页面配置里复制一份通知、定时任务或节点定义。

怎样选择合适的资源​

需求使用资源关键关联
给开发工作区增加入口开发菜单开发阶段、放置区域和菜单顺序。
给逻辑流增加节点逻辑流节点定义节点类型必须有编辑和执行实现。
调用外部服务RPC 与 RPC 认证RPC 引用凭据，地址可引用统一配置。
定时执行逻辑计划任务Cron、逻辑流名称和执行数据。
接收或发送消息消息队列绑定绑定类型、目标、消费组和逻辑流。
初始化模型记录数据初始化定义目标模型、版本和匹配字段。
记录业务操作业务日志模板匹配规则、业务键和敏感字段。
给页面提供公共文案国际化语言包locale、启用状态和 messages。
调整应用入口结构模块树 Diff模块引用、菜单和权限编排。

这些资源通常与 业务模型、数据模型、WebAPI 模型、逻辑流模型、组织模型 和 权限模型 组合使用。资源提供触发、编辑或运行所需的公共定义，核心模型仍负责业务语义和授权边界。

常见问题​

JSON 能解析，为什么资源仍不可用？​

JSON 语法正确只说明文本可读取。继续检查文件后缀、发现目录、稳定标识、引用对象和运行时注册结果；有相应 Schema 时，还应校验结构与字段值。

为什么初始化文件更新后，已有记录没有变化？​

初始化执行器按匹配字段查找，已存在的记录会跳过。它用于补齐缺失数据，修改版本不会把它变成覆盖更新操作。

配了计划任务，为什么没有自动执行？​

先查定义是否已加载、调度器是否已注册该任务、Cron 是否有效，再检查目标逻辑流是否存在及执行日志。设计文件保存与运行环境中的任务注册需要分别确认。
