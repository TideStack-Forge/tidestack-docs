# 平台支撑资源

平台支撑资源把运行链路需要的公共定义放在合适的位置：开发平台需要导航和编辑器元数据，逻辑流需要节点目录，集成能力需要凭据、消息与调度，运维链路需要日志、初始化和错误码。它们各自服务一个明确的消费者，不承担业务模型的对象、关系和动作。

## 先确定资源服务谁

同名的“定义”可能处于不同链路。开发菜单服务的是开发工作区，菜单模型服务的是应用导航；逻辑流节点定义描述编辑器如何创建节点，节点实现才负责执行；计划任务定义描述周期触发，延迟任务则由运行时调度接口提交。

资源进入应用后通常经历三个阶段：文件或管理入口提交定义，专用 provider 发现并解析，运行时服务把它交给页面、逻辑流、接口或运维能力消费。某一阶段成功不代表后续阶段已经完成，例如保存计划任务不等于调度器已经注册，上传微前端包也不等于菜单已经出现。

## 开发工具定义

### 开发菜单

开发菜单定义开发平台的功能入口，与应用运行态菜单分别管理。`stage` 决定欢迎阶段或应用开发阶段，`placement` 决定放在主导航还是辅助区域。它不会成为用户应用的业务菜单。契约：`dev-menu.schema.json`。

| 属性 | 作用 | 说明 |
| --- | --- | --- |
| `fullName` | 菜单标识 | 唯一识别开发菜单。 |
| `title` | 菜单标题 | 开发平台导航中显示的名称。 |
| `url` | 跳转地址 | 指定开发工具或管理页面的入口。 |
| `icon` | 菜单图标 | 用于导航识别。 |
| `placement` | 放置区域 | `main` 为主导航，`secondary` 为次级导航，`all` 表示两者。 |
| `stage` | 展示阶段 | `welcome` 为欢迎页，`dev` 为应用开发阶段，`all` 表示两个阶段均展示。 |
| `showMode` | 打开方式 | 指定入口的展示方式。 |
| `order` | 展示顺序 | 控制同级菜单排序。 |
| `children` | 子菜单 | 嵌套组织下级开发入口。 |
| `extraProps` | 扩展属性 | 保存导航使用的附加信息，JSON 中按属性名展开。 |

### 逻辑流节点定义

节点定义是编辑器和运行时之间的共同契约：编辑器据此显示节点、生成属性表单、限制端口连接；运行时再根据 `type` 通过节点工厂找到已注册的节点构建器和执行实现。修改节点定义的属性名称会影响已保存逻辑流，新增节点类型必须同时有执行实现。契约：`flow-node.schema.json`。

| 属性 | 作用 | 说明 |
| --- | --- | --- |
| `type` | 节点类型 | 与运行时节点实现对应的类型标识。 |
| `label` | 节点标题 | 节点面板和画布中的显示名称。 |
| `icon` | 节点图标 | 节点的视觉标识。 |
| `iconBg` | 图标背景 | 指定图标背景色。 |
| `iconColor` | 图标颜色 | 指定图标前景色。 |
| `group` | 节点分组 | 组织节点选择面板。 |
| `shape` | 节点形状 | 指定画布上的节点形态。 |
| `description` | 节点说明 | 解释节点用途。 |
| `isTerminal` | 终结节点标记 | 声明该节点是否具有终结语义。 |
| `terminalKind` | 终结类型 | 区分具体的终结语义。 |
| `editorCapabilities` | 编辑器能力 | 声明编辑器对该节点提供的交互能力。 |
| `scaffold` | 初始结构 | 提供新建节点时的配置骨架。 |
| `portRules` | 端口规则 | 定义端口的数量、类型及连接约束。 |
| `properties` | 属性编辑项 | 描述节点参数的编辑表单。 |
| `svgs` | 矢量资源 | 提供节点使用的 SVG 资源。 |
| `order` | 展示顺序 | 控制节点在选择列表中的排序。 |

## 集成、通知与调度

### RPC 认证定义

RPC 定义通过凭据名称引用认证资源。认证类型决定如何把参数应用到请求；认证资源只保存给对应构建器消费的参数，RPC 模型保存引用名称。契约：`rpc-auth.schema.json`。

| 属性 | 作用 | 说明 |
| --- | --- | --- |
| `name` | 凭据标识 | 供 RPC 定义引用的稳定名称。 |
| `title` | 凭据标题 | 管理界面显示的名称。 |
| `type` | 认证类型 | 选择对应的凭据实现。 |
| `description` | 凭据说明 | 解释用途及所接入系统。 |
| `isEnabled` | 启用状态 | 控制该认证定义是否启用。 |
| `extraProps` | 认证参数 | 保存认证类型要求的专有参数，JSON 中按属性名展开。 |

凭据名称应保持稳定，实际认证参数按目标环境维护。停用或替换一份共享凭据前，先检查所有引用它的 RPC；不要将认证参数复制到多个逻辑流节点中。不同认证类型有自己的专有属性，需按对应实现配置。

### 通知模板

通知模板声明负载和渠道内容。通知服务负责解析接收人、选择渠道和投递；模板本身不产生审批任务，也不会替代消息队列。契约：`notification.schema.json`。

| 属性 | 作用 | 说明 |
| --- | --- | --- |
| `name` | 模板标识 | 发送通知时引用的名称。 |
| `title` | 模板标题 | 管理界面中的显示名称。 |
| `isEnabled` | 启用状态 | 控制模板是否可用。 |
| `payloadSchema` | 负载结构 | 约束发送通知需要提供的数据。 |
| `channel` | 渠道配置 | 按渠道标识保存内容模板和渠道所需参数。 |

发送时由调用方提供模板名称、接收对象和负载。模板内的字段引用应与 `payloadSchema` 和实际负载一致；渠道名称、内容格式和参数由已接入渠道解释。出现“模板可查到但未收到通知”时，还要检查接收人解析、渠道配置与投递记录。

### 消息队列绑定

绑定定义连接消息队列与应用。生产绑定描述消息写向哪里，消费绑定描述从哪里接收，并可将消息交给指定逻辑流。消费组、广播和路由键会改变投递语义，不能只改 `destination` 就认为是同一条通道。契约：`mq.schema.json`。

| 属性 | 作用 | 说明 |
| --- | --- | --- |
| `bindingType` | 绑定类型 | 区分生产与消费等绑定方式。 |
| `bindingName` | 绑定标识 | 应用内识别消息通道的名称。 |
| `destination` | 消息目标 | 指定消息主题或相应目标，由中间件适配器解释。 |
| `binder` | 绑定器 | 选择已配置的消息中间件绑定器。 |
| `group` | 消费组 | 定义消费者所属的分组。 |
| `contentType` | 内容类型 | 声明消息内容的媒体类型。 |
| `broadcast` | 广播标记 | 声明是否采用广播方式。 |
| `routingKey` | 路由键 | 提供消息路由使用的键。 |
| `flowName` | 消费逻辑流 | 指定消息到达后执行的逻辑流。 |
| `description` | 绑定说明 | 解释通道的用途。 |
| `extraProps` | 扩展配置 | 保存具体消息中间件所需的附加参数，JSON 中按属性名平铺。 |

消费绑定示例：

```json
{
  "bindingType": "consumer",
  "bindingName": "eventConsumer",
  "destination": "business.events",
  "group": "application",
  "contentType": "application/json",
  "flowName": "consumeEvent"
}
```

使用前需配置可用的消息绑定器，并提供 `consumeEvent` 逻辑流。当前逻辑流消费者把可转换为对象的消息体放入 `payload`，消息头放入 `headers`；消费逻辑应按这两个上下文入口读取数据。消息投递与业务处理不是同一个事务，业务逻辑应处理重复消息，失败后的重投策略则要按实际绑定器核对。

### 计划任务定义

计划任务按 Cron 表达式周期触发逻辑流。它描述可重复注册的周期任务；一次性延迟任务由运行时调度服务按提交时的到期时间管理，不使用这份定义。契约：`schedule.schema.json`。

| 属性 | 作用 | 说明 |
| --- | --- | --- |
| `name` | 任务标识 | 注册和管理计划任务使用的名称。 |
| `description` | 任务说明 | 解释定期处理的用途。 |
| `cron` | 触发表达式 | 指定周期执行时间。 |
| `flowName` | 目标逻辑流 | 指定任务触发时执行的逻辑流。 |
| `data` | 任务数据 | 提供逻辑流执行需要的上下文数据。 |

例如，下面的周期任务在每天凌晨 2 点调用已有逻辑流：

```json
{
  "name": "dailySummary",
  "description": "每日汇总",
  "cron": "0 0 2 * * ?",
  "flowName": "dailySummary",
  "data": { "source": "scheduler" }
}
```

这要求逻辑流已经存在。调度实现使用 Quartz 时，Cron 应遵循 Quartz 语法；任务的 `data` 作为本次逻辑流上下文传入。周期执行可能重复或失败，业务处理应考虑幂等性，并保留可定位任务名和执行结果的日志。

一次性延迟任务则调用 `Scheduler.scheduleOnce`，按指定时间或延迟时长触发，也可以按任务名称取消。它适合在业务运行期间安排后续工作，不需要给每个业务事件新增一份周期任务文件。

## 日志与数据准备

### 业务日志模板

业务日志模板按请求方法和 URL 匹配操作，再提取业务键和摘要。响应体是否保存、哪些字段脱敏，都在模板中明确；日志模板不是权限审计规则的替代品。契约：`business-log.schema.json`。

| 属性 | 作用 | 说明 |
| --- | --- | --- |
| `name` | 模板标识 | 唯一识别日志模板。 |
| `httpMethod` | 请求方法 | 限定该模板匹配的 HTTP 方法。 |
| `url` | 匹配地址 | 限定需要记录的请求地址。 |
| `moduleName` | 所属模块 | 标明操作归属的业务模块。 |
| `operation` | 操作名称 | 标识被记录的业务操作。 |
| `level` | 日志级别 | 指定记录采用的级别。 |
| `businessKeyName` | 业务键名称 | 指定用于关联业务记录的键。 |
| `summaryTemplate` | 摘要模板 | 根据操作上下文生成日志摘要。 |
| `sensitiveFields` | 敏感字段 | 列出需要按日志规则保护的字段。 |
| `shouldSaveResponseBody` | 保存响应体 | 控制是否记录响应正文。 |

业务键应能定位被操作的业务记录，摘要应让维护人员看懂发生了什么。响应体可能很大，也可能包含敏感数据，只有确有追溯需要时才保存，并同步核对脱敏字段。模板命中了请求不表示操作成功，分析日志时还应结合结果和异常。

### 数据初始化定义

初始化计划把一批基座或应用初始记录分成多个数据块。每个数据块指定目标模型、版本、匹配字段和记录，初始化执行器据此判断记录是否已经存在。计划至少包含一个 block；它不是业务导入任务的通用替代品。契约：`data-init.schema.json`。

| 属性 | 作用 | 说明 |
| --- | --- | --- |
| `id` | 计划标识 | 唯一识别初始化计划。 |
| `version` | 计划版本 | 记录初始化内容版本，未指定时使用默认版本。 |
| `blocks` | 数据块集合 | 保存各个目标模型的初始化定义，至少包含一个数据块。 |
| `blocks[].id` | 数据块标识 | 在计划内识别数据块。 |
| `blocks[].targetModel` | 目标模型 | 引用需要初始化的数据模型。 |
| `blocks[].version` | 数据块版本 | 记录该数据块的内容版本。 |
| `blocks[].matchFields` | 匹配字段 | 用于判断目标记录是否已经存在。 |
| `blocks[].records` | 初始记录 | 列出需要补齐的记录数据。 |

```json
{
  "id": "application.defaults",
  "version": "1",
  "blocks": [
    {
      "id": "defaults",
      "targetModel": "sample",
      "matchFields": ["code"],
      "records": [{ "code": "default", "title": "默认项" }]
    }
  ]
}
```

示例要求 `sample` 数据模型已存在，并有相应字段。`matchFields` 不可为空，每条记录必须包含所有匹配字段；这些字段共同用于查找已有记录。当前执行器找到记录后跳过，只插入缺失记录，不会用定义中的新内容覆盖已有记录。

数据块未指定版本时使用计划版本；执行台账记录计划、数据块、目标模型、版本和内容摘要。增加版本不等于强制覆盖业务数据，需要更新已有记录的业务迁移应使用相应迁移方案。

## 公共文案与结构定义

### 国际化语言包

语言包按 locale 保存页面和公共能力使用的文案。`messages` 是分组键到翻译文本的映射，语言包启用后才能被查找；它不会自动翻译业务数据内容。契约：`i18n.schema.json`。

| 属性 | 作用 | 说明 |
| --- | --- | --- |
| `locale` | 语言标识 | 指定语言与地区，例如 `zh-CN`。 |
| `name` | 语言名称 | 语言选择与管理界面中的显示名称。 |
| `version` | 资源版本 | 记录语言包的版本。 |
| `enabled` | 启用状态 | 控制语言包是否启用。 |
| `isDefault` | 默认语言 | 声明是否作为默认语言。 |
| `direction` | 排版方向 | 声明从左向右或从右向左的文字方向。 |
| `timestamp` | 资源时间 | 记录语言包的时间信息。 |
| `messages` | 文案映射 | 先按文案分组，再按文案键保存翻译文本。 |

例如，菜单翻译按 `menu` 分组组织：

```json
{
  "locale": "en-US",
  "name": "English",
  "version": "1.0.0",
  "enabled": true,
  "isDefault": false,
  "direction": "LTR",
  "messages": {
    "menu": { "settings.title": "Settings" }
  }
}
```

这里的键应对应平台实际消费的文案路径。修改标题不会自动重命名翻译键；缺少翻译时的显示由具体消费能力决定，不应靠同一个键保存含义不同的文本。

### 岗位定义

岗位定义声明可复用的岗位类别；组织树中的实际岗位另行记录编制、负责人和任职。修改定义会影响引用该岗位类别的实际岗位显示，具体任职仍在组织模型中维护。契约：`position.schema.json`。

| 属性 | 作用 | 说明 |
| --- | --- | --- |
| `key` | 岗位编码 | 引用预定义岗位的稳定标识。 |
| `name` | 岗位名称 | 岗位类别的显示名称。 |
| `level` | 岗位层级 | 保存岗位的分级信息。 |
| `description` | 岗位说明 | 解释岗位职责。 |

### 错误码定义

错误码把稳定标识、业务编码和提示模板组织在一起。文件内容是定义数组；调用方应依赖稳定 `code` 或 `bizCode`，不要把提示文本当作程序分支条件。契约：`error-code.schema.json`。

| 属性 | 作用 | 说明 |
| --- | --- | --- |
| `code` | 错误编号 | 错误的数值标识。 |
| `title` | 错误标题 | 便于识别错误类别的简短名称。 |
| `defaultMessageTemplate` | 默认提示模板 | 在没有其他文案覆盖时生成错误提示。 |
| `bizCode` | 业务错误编码 | 提供面向业务或外部调用方的错误标识。 |
| `category` | 错误分类 | 按用途组织错误定义。 |
| `description` | 错误说明 | 解释原因及适用条件。 |
| `enabled` | 启用状态 | 控制错误定义是否启用。 |

### 模块树重组定义

模块树 Diff 保存新增、删除和修改模块的变更项。文件内容为变更数组，运行时应用到原始模块后再编排菜单和权限。它调整应用结构，不删除业务模型、页面或数据。契约：`modules-diff.schema.json`。

| 属性 | 作用 | 说明 |
| --- | --- | --- |
| `diffType` | 变更类型 | 指定 `add`、`remove` 或 `modify`。 |
| `fullName` | 目标模块 | 引用需要变更的模块全名。 |
| `parent` | 目标父模块 | 指定重组后的父级位置。 |
| `title` | 模块标题 | 提供需要覆盖的显示名称。 |
| `description` | 模块说明 | 提供需要覆盖的职责说明。 |
| `icon` | 模块图标 | 提供需要覆盖的图标。 |
| `order` | 展示顺序 | 提供需要覆盖的同级排序。 |
| `menu` | 主菜单引用 | 指定调整后的主菜单。 |
| `subMenus` | 子菜单引用 | 修改时非空列表整体替换，空列表沿用原值。 |
| `authorities` | 权限引用 | 修改时非空列表整体替换，空列表沿用原值。 |

## 资源怎样进入运行链路

1. **提交**：资源可以来自应用资源目录、JAR 内嵌 metadata 或管理界面。不同资源使用各自的文件后缀和目录。
2. **解析**：provider 读取定义并转换为对应的模型；解析失败时应查看资源诊断，不要用一份相似 JSON 代替正式契约。
3. **注册**：registry、provider 或 runtime service 建立运行时索引。刷新元数据后，旧缓存是否失效取决于具体资源服务。
4. **消费**：页面、编辑器、逻辑流、接口、调度器或日志服务按自己的契约消费资源。
5. **验证结果**：检查真正的消费方是否已发现资源，例如逻辑流节点能否执行、计划任务是否已注册、消息消费是否能触发目标逻辑流。

资源的发现、校验和运行时注册必须使用各模块的正式扩展点。不要在业务模型或页面配置里复制一份通知、定时任务或节点定义。

## 怎样选择合适的资源

| 需求 | 使用资源 | 关键关联 |
| --- | --- | --- |
| 给开发工作区增加入口 | 开发菜单 | 开发阶段、放置区域和菜单顺序。 |
| 给逻辑流增加节点 | 逻辑流节点定义 | 节点类型必须有编辑和执行实现。 |
| 调用外部服务 | RPC 与 RPC 认证 | RPC 引用凭据，地址可引用统一配置。 |
| 定时执行逻辑 | 计划任务 | Cron、逻辑流名称和执行数据。 |
| 接收或发送消息 | 消息队列绑定 | 绑定类型、目标、消费组和逻辑流。 |
| 初始化模型记录 | 数据初始化定义 | 目标模型、版本和匹配字段。 |
| 记录业务操作 | 业务日志模板 | 匹配规则、业务键和敏感字段。 |
| 给页面提供公共文案 | 国际化语言包 | locale、启用状态和 messages。 |
| 调整应用入口结构 | 模块树 Diff | 模块引用、菜单和权限编排。 |

这些资源通常与 [业务模型](../business-model/)、[数据模型](../data-model/)、[WebAPI 模型](../webapi-model/)、[逻辑流模型](../logicflow-model/)、[组织模型](../organization-model/) 和 [权限模型](../authority-model/) 组合使用。资源提供触发、编辑或运行所需的公共定义，核心模型仍负责业务语义和授权边界。
## 常见问题

### JSON 能解析，为什么资源仍不可用？

JSON 语法正确只说明文本可读取。继续检查文件后缀、发现目录、稳定标识、引用对象和运行时注册结果；有相应 Schema 时，还应校验结构与字段值。

### 为什么初始化文件更新后，已有记录没有变化？

初始化执行器按匹配字段查找，已存在的记录会跳过。它用于补齐缺失数据，修改版本不会把它变成覆盖更新操作。

### 配了计划任务，为什么没有自动执行？

先查定义是否已加载、调度器是否已注册该任务、Cron 是否有效，再检查目标逻辑流是否存在及执行日志。设计文件保存与运行环境中的任务注册需要分别确认。
